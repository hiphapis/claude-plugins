# 공통 룰 카탈로그

- 버전: **v5** (2026-10-30). 버전별 변경은 파일 끝 「변경 이력」에 있다.
- 형식: `### <ID> <제목> <별점> <전제 태그>` 다음에 **룰**과 **이유**를 적는다. 별점은 모든 프로젝트에 기본으로 깔 가치를 나타낸다(★5가 가장 높음).
- **Orca 사용이 기본 전제다.** 이 룰은 Orca 위에서 오케스트레이터·워커로 일하는 방식을 기준으로 정했으므로, Orca 룰은 태그 없이 모든 리포에 들어간다.
- 전제 태그: `[gh]` GitHub 이슈 사용 · `[vault]` `docs/` 문서 체계 · `[ko]` 한국어 문서 · `[personal]` 개인 선호. 태그가 없으면 모든 리포에 해당한다.
- 처리 표시: `[outward]` 리포 밖으로 나가는 행동(push, 이슈 종료, 배포)을 에이전트가 묻지 않고 하게 만드는 룰. 기존 룰에 대응 문장이 없어도 넣기 전에 사용자에게 확인한다. 룰의 일부만 해당하면(R-ISSUE-07의 ④ 이슈 닫기, R-ORCA-12의 "이슈를 닫은 뒤 다시 감사") 그 부분만 확인 대상이다.
- 전제 태그가 둘 이상이면 모두 충족해야 한다.
- 도구 의존: 아래 룰은 해당 도구가 있어야 지킬 수 있다. 스킬은 적용할 때 이 표로 도구 유무를 확인한다(SKILL.md 3단계).

  | 도구 | 확인 | 설치 | 기대는 룰 |
  |---|---|---|---|
  | Orca (`orca` CLI) | `command -v orca` | 안내만: 데스크톱 앱 <https://github.com/stablyai/orca> | 카탈로그 전체의 전제. 직접 쓰는 룰: R-ORCA 전부, R-ROLE-06~08·10, R-SPEC-05~07, R-ISSUE-06·07 |
  | `gh` CLI | `command -v gh` | `brew install gh` → 사용자가 `gh auth login` | `[gh]` 룰 |
  | worktree-teardown 플러그인 | 세션 스킬 목록에 `worktree-teardown:worktree-teardown` | `claude plugin install worktree-teardown@hiphapis` → 세션 재시작 | R-ORCA-12, R-ISSUE-07(감사 부분) |
  | oh-my-claudecode `ccg` | 세션 스킬 목록에 `oh-my-claudecode:ccg`, `command -v codex`·`command -v gemini` | `claude plugin install oh-my-claudecode --marketplace Yeachan-Heo/oh-my-claudecode` → 세션 재시작. Codex·Gemini CLI는 안내만 | R-ROLE-09 |
  | `ego-browser` 스킬 | 세션 스킬 목록에 `ego-browser` | 안내만: ego 앱이 함께 설치함 | R-BASE-05 |
- R-ROLE-04의 모델·effort는 리포가 채울 값이 아니라 **의도적으로 내장한 현재값**이다. 바뀌면 이 파일만 고치고 버전을 올린다.
- 버전을 올릴 때 바뀐 룰에는 제목 끝에 `(vN 변경)`·`(vN 추가)`를 붙인다.

## 1. 원칙·커뮤니케이션

### R-BASE-01 모르면 묻는다 ★★★★★
- 룰: 지시가 불명확하거나 기존 결정과 부딪히는 사실이 나오면 임의로 정하지 말고 멈춰서 묻는다. 판정 기준을 에이전트가 넓히지 않고, 결정되지 않은 것은 미결정 상태로 보고한다.
- 이유: 에이전트가 임의로 정한 것을 되돌리는 비용이 질문 한 번보다 훨씬 크다. 이해가 속도보다 먼저다.

### R-BASE-02 제품 판단은 사람이 한다 ★★★
- 룰: 제품 판단과 디자인 방향은 사용자가 정한다. 에이전트는 선택지와 근거를 내고 대신 정하지 않는다.
- 이유: 에이전트의 범위를 분명히 해 월권을 막는다.

### R-BASE-03 추천에는 위험 근거와 모순을 적는다 ★★★★
- 룰: 추천할 때는 그 안의 위험 근거를 함께 적고, 앞서 낸 이슈·메시지의 방향과 어긋나면 그 점을 짚는다.
- 이유: 사용자가 모순을 모른 채 승인하는 일을 막는다.

### R-BASE-04 출력은 한글로 ★★★★★ [personal] [ko]
- 룰: 사용자에게 보이는 출력은 진행 안내 한 줄, 커밋 본문, PR 설명까지 모두 한글·존댓말로 간결하게 쓴다. 코드·명령·경로·식별자·고유명사·외부 문서 제목은 원문을 유지하고, 필요하면 영어 용어를 괄호로 병기한다("캐시 미스(cache miss)").
- 이유: 사용자 선호다. 번역투를 피하고 자연스러운 한국어로 쓴다.

### R-BASE-05 브라우저 확인은 ego-browser로 ★★★★ [personal]
- 룰: 브라우저로 페이지를 열거나 화면을 확인할 때는 `/ego-browser` 스킬만 쓴다.
- 이유: 사용자의 로그인 세션과 개인 맥락을 그대로 쓸 수 있다.

### R-BASE-06 기존 자산과 겹치면 먼저 정렬한다 ★★★★
- 룰: 기존 자산(다른 팀의 도구·하네스·서비스)과 겹치는 기능을 새로 만들기 전에 그 오너와 먼저 정렬한다.
- 이유: 같은 목표의 프로젝트가 "기존 작업과 중복"으로 착수 전에 중단된 전례가 있다.

### R-BASE-07 기각된 계획은 근거로 쓰지 않는다 ★★★★ [vault]
- 룰: 기각되거나 이력으로만 남긴 계획서는 구현·제안의 근거로 쓰지 않는다. 다시 꺼내려면 사용자 결정과 ADR이 먼저다.
- 이유: 죽은 계획이 되살아나 작업을 오염시키는 걸 막는다.

### R-BASE-08 프로젝트 규칙이 스킬 문구보다 우선한다 ★★★★
- 룰: 스킬 본문과 프로젝트 규칙(`AGENTS.md`·`docs/` 규칙 문서)이 충돌하면 프로젝트 규칙을 따른다.
- 이유: 정책 층의 우선순위가 분명해진다. 스킬은 범용이고 프로젝트 규칙은 그 리포에 맞춘 결정이다.

### R-BASE-09 공유 문서에 내 목표를 내세우지 않는다 ★★★
- 룰: 동료가 보는 공유 문서에서는 내 개인 목표·KR을 앞세우지 않고, 공통 관심사를 명분으로 쓴다.
- 이유: 협업 문서가 설득력을 잃지 않는다.

### R-BASE-10 도구가 없으면 우회하지 않고 묻는다 ★★★★★ (v3 추가)
- 룰: 룰이 요구하는 도구(Orca, `gh`, 스킬 등)가 없거나 실패하면 비슷한 다른 수단으로 우회하지 말고 멈춰서 사용자에게 묻는다. 예: `orca worktree`가 없다고 `git worktree add`로 대신하지 않는다. 단계를 건너뛰었으면 완료 보고에 그 사실과 이유를 적는다.
- 이유: 우회 수단은 룰이 막으려던 문제(Orca 상태 불일치, 검증 누락)를 그대로 다시 만든다. R-BASE-01을 도구 부재 상황에 구체화한 것이다.

## 2. 역할 분담·라우팅

### R-ROLE-01 코드는 한 줄이라도 워커가 쓴다 ★★★★★
- 룰: 코드·테스트·설정 코드(`package.json`·Dockerfile·compose·SQL 포함)는 워커가 쓴다. 오케스트레이터는 직접 편집하지 않는다. "한 줄", "간단해서", "급해서"는 예외 사유가 아니다.
- 이유: 작성자와 검증자를 구조적으로 분리한다. 리뷰 워커가 오케스트레이터가 놓친 실제 결함을 잡아낸 사례가 있다.

### R-ROLE-02 오케스트레이터가 직접 하는 일의 목록 ★★★★★
- 룰: 오케스트레이터가 직접 하는 일은 스펙, 이슈, `docs/**`, `AGENTS.md`, `.gitignore` 같은 비코드 설정, 출처를 적은 데이터 스냅샷, 로컬 main ff 머지, 테스트 **재실행**(편집 아님)이다. 나머지는 워커에게 넘긴다.
- 이유: 경계를 목록으로 못 박아 매번 고민하지 않게 한다.

### R-ROLE-03 오케스트레이터는 테스트 파일을 고치지 않는다 ★★★★
- 룰: 오케스트레이터는 `*.test.*`·`*.spec.*`를 작성·수정하지 않는다. 이름 변경·파일 이동 같은 기계적 조작만 예외다.
- 이유: 통과시키려고 테스트를 느슨하게 만드는 경로를 막는다.

### R-ROLE-04 현재 워커 설정은 한 곳에 현재값만 ★★★★★ (v5 변경)
- 룰: 워커의 에이전트·모델·effort는 규칙 문서 상단 한 곳에 **현재값만** 적고(이력 없이), 디스패치할 때마다 작업 등급에 맞는 값을 그대로 명시한다. `--effort`는 `--model` 없이 쓸 수 없다. 현재값(모두 `--agent claude`):

  | 역할 | 등급 | 기준 | 설정 |
  |---|---|---|---|
  | 구현 | 기계적 | 스펙이 줄 단위로 정해짐: 일괄 치환, 생성물 갱신, 의존성 버전 올리기 | `--model claude-sonnet-5-5 --effort low` |
  | 구현 | **일반(기본)** | 결정이 끝난 스펙을 그대로 구현 | `--model claude-sonnet-5-5 --effort medium` |
  | 구현 | 어려움 | 원인 불명 버그, 동시성·상태 관리, 여러 모듈에 걸친 리팩터, 성능 | `--model claude-opus-5-5 --effort high` |
  | 리뷰 | **일반(기본)** | 고위험이 아닌 모든 리뷰 | `--model claude-opus-5-5 --effort high` |
  | 리뷰 | 고위험 | 인증·권한·결제·데이터 삭제·외부 입력 처리 | `--model claude-opus-5-5 --effort xhigh` |

  - 등급은 오케스트레이터가 디스패치 전에 정하고, 등급과 이유를 스펙에 한 줄 적는다. 애매하면 한 단계 위로 보낸다.
  - 같은 작업이 리뷰에서 두 번 반려되면 구현 등급을 한 단계 올린다.
  - 설계는 워커 등급이 아니다. 설계 비중이 큰 작업은 오케스트레이터와 사용자가 설계를 먼저 정해 스펙에 담고(R-SPEC-01, R-BASE-02), 구현은 "어려움"으로 보낸다.
  - 큰 diff는 effort를 올리지 말고 영역별로 나눠 리뷰 워커 여러 명에게 병렬로 맡긴다. 고위험 영역만 "고위험" 등급으로 리뷰한다.
- 이유: 설정이 바뀌면 한 곳만 고치면 된다. "평상시/임시" 이력이 섞이면 지금 무엇을 써야 하는지 헷갈린다. 등급은 어려운 구현과 위험한 리뷰에만 비용을 더 쓰기 위해 두되, 오케스트레이터의 판단이 흔들리지 않게 구현 셋·리뷰 둘로 제한한다.

### R-ROLE-05 세 가지 경로 ★★★★★
- 룰: 작업마다 경로를 먼저 정한다. **inline**은 문서·비코드 설정·기계적 조작(이동·이름 변경)만 다루고 코드는 한 줄도 없다. **full handoff**는 넘기고 끝나는 단발 구현·조사다. **supervised**는 다단계·중간 질의응답·병렬 추적이 필요할 때 쓴다. 판단 기준은 "완료를 기다렸다가 내가 결정해야 하는가"이다(예 → supervised).
- 이유: 오타 하나에 orchestration 4콜을 쓰는 과설계와, 감독이 필요한 일을 방치하는 일을 둘 다 막는다.

### R-ROLE-06 감독이 필요 없으면 orchestration을 쓰지 않는다 ★★★
- 룰: 감독을 요구하지 않는 작업에 `task-create`·`dispatch --inject`·`check --wait`를 쓰지 않는다.
- 이유: 오케스트레이터 소유의 불필요한 추적 상태가 남는다.

### R-ROLE-07 경로별 종결 조건 ★★★★ (v4 변경)
- 룰: inline은 문서 전용 게이트(린터)와 완료 보고로 끝낸다. supervised는 게이트 green + `worker_done --outcome succeeded` + 오케스트레이터가 diff와 게이트 출력을 직접 확인해야 끝난다. full handoff는 소유권이 넘어갔으므로 워커가 스스로 종결한다. 다만 결과를 받기로 한 full handoff는 R-ORCA-15대로 대기해 완료를 확인한 뒤 supervised와 같은 기준으로 끝낸다.
- 이유: 누가 무엇을 근거로 판정하는지가 분명해진다.

### R-ROLE-08 통과 판정은 독립 증거로 ★★★★★
- 룰: 워커의 `worker_done` 요약만으로 "통과"를 선언하지 않는다. 별도 리뷰 워커의 `succeeded`나 오케스트레이터가 독립 재실행한 JSON 리포트가 있어야 한다. 구현 워커 혼자 "완료"를 선언하지 않는다.
- 이유: 자기가 한 작업을 자기가 승인하는 편향을 막는다.

### R-ROLE-09 되돌릴 수 없는 변경만 ccg ★★★ (v3 변경)
- 룰: ccg 3중 합의(`/oh-my-claudecode:ccg`)는 실패하면 되돌릴 수 없는 변경에만 쓴다 — 운영 데이터 삭제·되돌릴 수 없는 마이그레이션, 인증·권한 모델 변경, 과금·결제 로직. 일반 PR·머지·배포는 게이트와 독립 리뷰(R-ROLE-08)로 충분하므로 쓰지 않는다. 해당하는지 애매하면 ccg를 돌리지 말고 사용자에게 묻는다.
- 이유: ccg는 토큰과 시간이 많이 들고, 일상적인 머지·배포의 정확성은 게이트와 리뷰 워커가 이미 확인한다. 기준을 "밖으로 나가는가"가 아니라 "되돌릴 수 있는가"로 두어 정말 필요한 때만 쓴다.

### R-ROLE-10 "워크트리로 진행"은 세션 이동 ★★★ [personal]
- 룰: 사용자가 "워크트리로 만들어서 진행하자"고 하면 워커를 띄우지 말고 Orca로 워크트리를 만든 뒤 이 세션을 그리로 옮겨 진행한다. 이때도 통과 판정은 독립 리뷰로 받는다.
- 이유: 사용자는 같은 맥락을 가진 세션이 이어서 일하길 원한다.

## 3. 스펙·디스패치

### R-SPEC-01 스펙 템플릿 ★★★★★
- 룰: 워커 스펙은 다음 절로 쓴다. ① 작업 환경(이슈 번호, 워크트리, `.env`·untracked 자산 준비 절차) ② 배경 — "이미 조사됨, 재조사 불필요"(파일:줄 근거) ③ 결정 사항 — "그대로 구현, 대안 설계 금지" ④ 반드시 고칠 호출부 — "목록이 전부라고 가정하지 말고 grep으로 전수 확인" ⑤ 테스트로 고정할 지점 ⑥ 공통 규칙 블록(게이트·테스트·커밋·막히면).
- 이유: 재조사, 설계 이탈, 호출부 누락을 막는다.

### R-SPEC-02 순차 의존은 이유와 함께 ★★★★
- 룰: 순차 의존이 있으면 순서와 병렬 금지 이유(공유 파일 등)를 스펙에 적는다.
- 이유: 병렬 실행으로 생기는 충돌을 막는다.

### R-SPEC-03 공통 블록은 파일로 재사용 ★★★
- 룰: 스펙의 공통 규칙 블록은 파일로 두고 `cat spec.md common.md`처럼 이어 붙인다. 확정된 제약은 빠짐없이 복사한다.
- 이유: 매번 다시 쓰지 않아도 되고 누락도 없다.

### R-SPEC-04 디스패치 전 스택·제약 재확인 ★★★★
- 룰: 스택과 핵심 제약은 디스패치 전에 사용자에게 다시 확인한다.
- 이유: 브리프의 제약을 그대로 실행했다가 사용자 결정이 달라 전량 재작업한 적이 있다.

### R-SPEC-05 워커는 문서를 건드리지 않는다 ★★★★
- 룰: 위임받은 워커는 `docs/**`·`*.md`를 수정하지 않는다. 문서화할 발견은 `worker_done` 본문에 담아 넘기고, 문서는 오케스트레이터가 쓴다.
- 이유: 문서 정본의 관리 주체를 하나로 둔다.

### R-SPEC-06 막히면 묻는 통로 ★★★
- 룰: 워커는 설계 판단이 필요하거나 결정 사항과 충돌하는 사실을 발견하면 `orca orchestration ask`로 묻는다. 오케스트레이터는 `orca orchestration reply`로 답하고, ack한 뒤 계속 기다린다.
- 이유: 질의응답 때문에 대기 루프가 끊기지 않는다.

### R-SPEC-07 worker_done 형식 ★★★
- 룰: `worker_done`은 워커가 한 번만 보내고 `--outcome`과 `--files-modified`를 채운다. 유효한 `worker_done`은 task를 자동으로 completed 처리하므로 `task-update`를 또 부르지 않는다.
- 이유: 판정 입력이 정형화되고 상태가 이중으로 갱신되지 않는다.

## 4. Orca 워크트리

### R-ORCA-01 이슈 하나에 워크트리 하나 ★★★★★
- 룰: 이슈 하나에 독립 Orca 워크트리 하나를 쓴다. main 체크아웃에서는 코드를 고치지 않는다.
- 이유: 병렬 작업이 서로 오염되지 않고, 실패하면 통째로 버릴 수 있다.

### R-ORCA-02 워크트리는 Orca로 만든다 ★★★★
- 룰: 워크트리는 `orca worktree create`로 만들고 `--base-branch main`을 명시한다. 띄운 뒤 `git worktree list`로 HEAD를 확인한다. `.claude/worktrees/`나 `git worktree add`로 직접 만들지 않는다.
- 이유: 직접 만든 워크트리는 Orca 앱에 보이지 않고, 나중에 등록할 수도 없다.

### R-ORCA-03 워커는 부모 밑에 중첩 ★★★
- 룰: 워커 워크트리는 Orca 사이드바에서 오케스트레이터 워크트리 밑에 나오게 한다. 띄우는 경로마다 방법이 다르다.
  - `orca worktree create`: `--parent-worktree "id:$ORCA_WORKTREE_ID"`를 명시한다. `--no-parent`는 정말 무관한 작업에만 쓴다.
  - `orca orchestration worker-start`: `--worktree new-child`를 쓴다. `new-top-level`은 원격 서버(여기서는 `new-child`가 안 됨)나 무관한 작업에만 쓴다.
  - 부모를 생략하면 Orca가 호출 위치에서 추론하는데, 실패하면 루트에 생긴다. 그래서 늘 명시한다.
- 이유: 사이드바에서 lineage가 보인다. lineage와 base(`--base-branch`)는 별개라서 부모를 지정해도 기준 브랜치는 바뀌지 않는다.

### R-ORCA-04 current 공유는 좁게 ★★★★
- 룰: `--worktree current`는 같은 이슈의 후속 작업이거나 비코드 예외일 때만 쓴다. 미커밋 변경이 있다는 이유로 새 워크트리 생성을 건너뛰지 않는다.
- 이유: 격리 원칙이 슬그머니 무너지는 걸 막는다.

### R-ORCA-05 워커가 읽을 자료는 먼저 커밋 ★★★★★
- 룰: 워커가 읽어야 할 문서·데이터는 디스패치 전에 main에 커밋한다. gitignore 대상(`.env` 등)은 스펙에 복사 절차를 적는다.
- 이유: untracked·ignored 파일은 새 워크트리에 따라오지 않는다.

### R-ORCA-06 공용 파일의 소유자는 한 명 ★★★★
- 룰: 여러 워커가 같은 파일(`.gitignore`, 패키지 매니페스트 등)을 건드리지 않게 한 명에게 소유를 주거나, 오케스트레이터가 먼저 커밋한다.
- 이유: 병렬 머지 충돌을 막는다.

### R-ORCA-07 supervised 전제 확인 ★★★
- 룰: supervised orchestration을 시작하기 전에 `TERM_PROGRAM=Orca`이고 `orca status --json`이 ready인지 확인한다.
- 이유: Orca 밖에서 orchestration 명령이 실패하는 걸 미리 막는다.

### R-ORCA-08 대기 규칙 ★★★★
- 룰: 독립 태스크는 모두 만들고 모두 start한 뒤에 기다린다. `check --wait`는 Run당 하나만 걸고, 대기 프로세스를 kill하지 않는다. 타임아웃이나 `{count:0}`은 실패가 아니라 체크포인트다(코딩은 15～60분이 정상). heartbeat 배달은 ack한 뒤 다시 기다린다.
- 이유: 순차 대기로 시간을 버리지 않고, kill로 생기는 `waiter_exists` 잠김을 피한다.

### R-ORCA-15 워커 완료를 놓치지 않게 대기를 건다 ★★★★★ (v4 추가)
- 룰: 워커가 끝났다는 사실은 오케스트레이터에게 저절로 오지 않는다. 오케스트레이터는 사용자 메시지가 오거나 자기가 건 백그라운드 명령이 끝날 때만 다시 깨어난다. 그래서 결과를 받아야 하는 워커에는 늘 대기를 걸어 둔다.
  - 결과를 받아 게이트 재실행·리뷰·머지를 해야 하는 작업은 R-ROLE-05 기준대로 supervised(`check --wait`)로 띄운다.
  - full handoff(`orca worktree create --prompt`)로 띄웠는데 결과를 받아야 하면, 띄운 같은 턴에 워커 터미널마다 대기를 백그라운드로 건다. 워커가 프롬프트를 받기 전에 대기가 바로 끝나지 않게 짧게 지연한 뒤 시작한다. 예: `sleep 20 && orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 3600000`를 `run_in_background`로 실행.
  - 대기가 끝나면 곧바로 `git log main..HEAD`와 `orca terminal read` 출력으로 완료를 확인한다. `tui-idle`은 `status: running`으로도 끝날 수 있으니 대기가 끝난 것만으로 완료로 보지 않는다. 아직 일하는 중이면 다시 건다.
  - `orca terminal send`로 후속 지시(리뷰 반영 등)를 보냈으면 같은 턴에 대기를 다시 건다.
  - 대화 요약이나 세션 재개 직후에는 대기가 사라졌다고 보고, 진행 중인 워커마다 대기를 다시 건다. supervised에서 `waiter_exists`가 나오면 이전 대기가 아직 살아 있다는 뜻이므로 kill하지 않는다(R-ORCA-08). 그 대기가 이 세션의 백그라운드 작업에 없으면(세션 재개) 사용자에게 알린다.
  - "진행 중"이라고 보고만 하고 대기 없이 턴을 끝내지 않는다.
- 이유: 워커 둘이 끝났는데 대기가 걸려 있지 않아, 사용자가 지적할 때까지 오케스트레이터가 아무것도 하지 않은 적이 있다. 결과가 필요한 작업을 완료 신호가 없는 full handoff로 띄웠고, 대화가 요약되면서 대기 맥락도 사라졌다.

### R-ORCA-09 리뷰 워커는 같은 워크트리의 새 터미널 ★★★★
- 룰: 구현 `worker_done` 뒤 같은 워크트리에 새 터미널로 리뷰 워커를 붙여 diff 확인·독립 재실행·스펙 대조를 맡긴다.
- 이유: 구현 맥락과 분리된 리뷰가 된다.

### R-ORCA-10 release 전에 머지 ★★★★★
- 룰: 순서는 리뷰 `worker_done` → 머지 → `worker-release`다. 머지하기 전에 마지막 dispatch를 release하지 않는다.
- 이유: 마지막 소유 dispatch가 release되면 Orca가 워크트리와 브랜치를 회수한다. 실제로 브랜치를 잃은 적이 있다.

### R-ORCA-11 main 병합 직후 의존성부터 ★★★★
- 룰: 오래 산 워크트리에 main을 병합한 직후에는 의존성 설치와 코드 생성·마이그레이션부터 돌린다.
- 이유: 안 하면 `Cannot find module`이 무더기로 떠서 우리 변경이 깨진 것처럼 보인다.

### R-ORCA-12 머지 직후 teardown 감사 ★★★★★ [outward]
- 룰: 브랜치를 머지하고 워커를 해제할 때마다 `/worktree-teardown:worktree-teardown` 감사를 돌린다. SAFE면 에이전트가 `orca worktree rm`으로 지운다(`--force`, `git worktree remove`, `rm -rf`는 쓰지 않음). BLOCKED면 지적된 항목을 처리하고 다시 감사한다. 이슈가 아직 열려 있어 BLOCKED면 이슈를 닫은 뒤 다시 감사한다. 보존할 워크트리에는 `git worktree lock`을 건다.
- 이유: 재생성할 수 없는 산출물(`.omc/` 등)이 사라지거나 Orca 상태가 어긋나는 걸 막고, 사용자가 손으로 지우는 일을 없앤다.

### R-ORCA-13 브랜치 보존·폐기는 사유를 기록 ★★★
- 룰: 미병합 브랜치는 감사 전에 병합을 끝낸다. 보존하거나 폐기하는 브랜치는 사유를 기록해야 완료다.
- 이유: 기록 없이 사라진 브랜치는 중복 구현으로 이어진다.

### R-ORCA-14 세션을 닫기 전에 남은 워크트리 확인 ★★★★
- 룰: 세션을 닫기 전에 내가 만든 워크트리가 남아 있는지 확인하고, 감사 결과(삭제 또는 BLOCKED 사유)를 완료 보고에 적는다.
- 이유: 사용자가 손으로 지우는 상황을 만들지 않는다.

## 5. GitHub 이슈 수명주기

### R-ISSUE-01 고치기 전에 이슈부터 ★★★★★ [gh]
- 룰: 코드든 문서든 고치기 전에 GitHub 이슈를 만든다. 본문에는 배경·목표·완료 기준·검증 방법을 적는다. 이슈나 워크트리를 만들다 실패하면 수정을 시작하지 않고 차단 상태를 보고한다.
- 이유: 작업의 정본과 완료 기준이 먼저 생긴다. 완료 기준이 없으면 "끝"을 판정할 수 없다.

### R-ISSUE-02 이슈 없이 하는 예외 ★★★★ [gh]
- 룰: 이슈 라벨·제목 상태 동기화, 규칙 문서의 단순 보정, 코드·DB·생성 자산을 건드리지 않는 문서·메타데이터 작업은 현재 환경에서 처리해도 된다. 범위가 넘어가면 즉시 이슈·워크트리 규칙으로 돌아간다.
- 이유: 사소한 작업까지 절차를 밟는 비용을 줄인다.

### R-ISSUE-03 스코프 단위로 이슈 재사용 ★★★ [gh]
- 룰: 같은 스코프의 후속 요청은 기존 이슈·워크트리를 재사용하고, 완료 기준이 다르면 새 이슈를 만든다.
- 이유: 이슈가 지나치게 쪼개지거나 뭉치지 않는다.

### R-ISSUE-04 상태 이모지와 라벨 ★★★★ [gh]
- 룰: 이슈 제목은 상태 이모지 하나로 시작하고 같은 라벨을 단다 — 📋 `ready to work` · 🚧 `in progress` · 👀 `in review` · ⛔ `blocked` · ⏸️ `on hold` · ✅ 완료(closed) · ❌ 취소(closed, not planned). 상태가 확정되지 않았으면 붙이지 않는다. 작업을 시작하면 🚧로 바꾸고 `ready to work`를 뗀다.
- 이유: `gh issue list`만으로 현황이 보인다.

### R-ISSUE-05 상태 정본은 라벨 ★★★ [gh]
- 룰: 상태의 정본은 라벨이다. Projects 보드는 라벨을 단방향으로 비추는 읽기 전용 화면이며 Status 필드를 직접 고치지 않는다. 보드를 정본으로 바꾸는 건 사람 협업자가 2명 이상이 될 때 재검토한다.
- 이유: 에이전트는 보드가 아니라 `gh issue view`를 읽는다. 정본은 작업자가 있는 곳에 둔다.

### R-ISSUE-06 진행 상황은 워크트리 코멘트로 ★★★
- 룰: 재현·구현·검증·차단처럼 의미 있는 상태 변화가 생기면 `orca worktree set --comment`로 갱신한다.
- 이유: 사이드바에서 진행 상황이 보인다.

### R-ISSUE-07 완료 순서 ★★★★★ [gh] [outward]
- 룰: ① 이슈에 변경·검증·남은 위험 코멘트 → ② 문서 정본 반영 → ③ 제목을 ✅로 바꾸고 `in progress` 제거 → ④ 이슈 닫기, Orca 워크트리 `completed` → ⑤ teardown 감사. ①이나 ②를 빠뜨리면 완료로 보고하지 않는다.
- 이유: 닫힌 이슈만 봐도 무엇이 어떻게 검증됐는지 남는다.

### R-ISSUE-08 이슈는 에이전트가 닫는다 ★★★★ [gh] [outward]
- 룰: 완료 기준(main 머지, 게이트 green, 독립 검증, 배포가 기준이면 프로덕션 확인)을 채우면 에이전트가 사용자 승인을 기다리지 않고 닫고, 머지 해시와 게이트 수치를 코멘트로 남긴다. 후속 요청이 남아 있으면 그것까지 끝낸 뒤 닫는다. 취소(❌)는 사용자가 정한다.
- 이유: `in review`에 쌓아 두고 기다리는 일을 없앤다.

## 6. 테스트·게이트

### R-TEST-01 테스트 스펙과 테스트 코드를 나눈다 ★★★★★
- 룰: 테스트 스펙(인수 기준·경계값·실패 시나리오)은 오케스트레이터가 쓰고, 테스트 코드 작성과 1차 실행은 워커가 하며 실행 로그를 증거로 낸다. 최종 판정은 리뷰 워커나 독립 재실행으로 한다.
- 이유: "무엇을 검증할지"와 "어떻게 검증할지"를 분리한다.

### R-TEST-02 게이트는 한 줄, 결과는 JSON ★★★★★
- 룰: 커밋 전 게이트 명령을 한 줄로 고정한다(예: typecheck·lint·build·test). 결과는 요약이 아니라 JSON 리포트로 확인하고 failed·skipped(pending)·todo가 모두 0이어야 통과다.
- 이유: `PASS (n)` 요약은 skip을 숨긴다.

### R-TEST-03 조건부 테스트는 수집에서 제외 ★★★
- 룰: 환경이 있어야 도는 테스트는 skip 마커 대신 수집 단계에서 제외한다(예: vitest `exclude`, pytest `collect_ignore`).
- 이유: "skipped 0" 기준이 흔들리지 않는다.

### R-TEST-04 래퍼 오탐부터 의심 ★★★
- 룰: 게이트가 실패로 보이면 래퍼 오탐을 먼저 의심하고 앱 디렉토리에서 직접 돌려 raw 출력으로 확인한다. 래퍼의 exit code도 그대로 믿지 않는다.
- 이유: 래퍼가 설정 파일을 못 찾아 실패를 잘못 알린 적이 있다.

### R-TEST-05 통합 테스트는 따로 보고 ★★★★
- 룰: 통합·E2E 테스트를 추가·변경했으면 실행 여부와 수치를 따로 보고한다. 단위 테스트 green을 통합 테스트의 근거로 삼지 않는다.
- 이유: 통합 테스트는 기본 `test` 명령에 빠져 있는 경우가 흔하다.

### R-TEST-06 없는 검증을 있는 척하지 않는다 ★★★★
- 룰: 없는 게이트를 돌린 것처럼 쓰지 않는다. 선택 게이트는 실행했을 때만 수치를 적는다. 수동 실행 로그만으로 "통과"를 주장하지 않는다.
- 이유: 거짓 완료의 흔한 변형이다.

### R-TEST-07 문서 전용 변경의 게이트 ★★★
- 룰: 문서만 바꾼 작업은 문서 린터만 돌리고, 보고에 "게이트 없음(문서 전용 변경)"이라고 명시한다.
- 이유: 문서 작업에 무거운 게이트를 강요하지 않으면서도 보고는 정직하게 한다.

### R-TEST-08 생성물 드리프트 검사 ★★★
- 룰: 스키마 등 생성물은 다시 생성한 뒤 `git status`가 비어 있는지 확인한다.
- 이유: 정본과 생성물이 어긋난 걸 기계적으로 잡는다.

### R-TEST-09 테스트 데이터 보호 ★★★★
- 룰: 테스트는 임시 DB 컨테이너와 임시 포트를 쓰고 끝나면 지운다. 파괴적 정리를 막는 가드에 걸리면 가드를 끄지 말고 올바른 대상을 주입한다.
- 이유: dev 데이터가 지워지는 사고를 막는다.

## 7. Git

### R-GIT-01 커밋 주체는 고친 사람 ★★★★★
- 룰: 코드 커밋은 코드를 고친 워커가 자기 브랜치에서 게이트를 돌린 뒤 한다. 오케스트레이터가 하는 커밋은 문서·비코드 설정 커밋과 로컬 main ff 머지뿐이다.
- 이유: 작성 주체와 커밋 주체가 일치한다.

### R-GIT-02 자동 커밋과 push 범위 ★★★★★ [outward] (v2 변경)
- 룰: 검증이 끝난 커밋은 "커밋할까요?"라고 묻지 않고 한다(상시 권한). 문서 전용 커밋은 push까지 자동으로 하고, 코드가 섞이면 커밋을 나눈다. 코드가 포함된 push·PR은 사용자가 한다. 다만 운영 배포까지 마친 작업은 에이전트가 push까지 한다. "커밋하지 마"라는 말이 있으면 즉시 멈춘다.
- 이유: 승인 왕복을 없애면서도 바깥으로 나가는 코드는 사람이 쥔다. 운영에 이미 나간 코드는 원격에도 있어야 운영과 원격이 어긋나지 않는다.

### R-GIT-03 경로를 명시해 add ★★★★★
- 룰: `git add .`·`git add -A`는 쓰지 않고 경로를 명시한다. 워커는 `git commit -- <경로>`로 pathspec을 격리한다.
- 이유: `.env` 같은 민감 파일이나, 같은 작업 트리를 쓰는 다른 세션의 staged 파일이 섞인 사고가 있었다.

### R-GIT-04 커밋 하나에 논리적 변경 하나 ★★★★
- 룰: 커밋 하나에는 논리적 변경 하나만 담는다. 리팩터·포맷·문서·테스트 추가는 따로 커밋하고, 큰 작업은 중간중간 끊는다. 기준은 파일 수가 아니라 "되돌릴 수 있는 최소 단위"다.
- 이유: revert와 bisect가 쉬워진다.

### R-GIT-05 커밋 메시지 ★★★★
- 룰: 제목은 무엇을 왜 바꿨는지 70자 안쪽으로 쓰고, 본문은 필요할 때만 쓴다. Conventional Commits 접두사는 선택이다. 이슈 근거 작업에는 `Refs #N`을 달고, 자동 종료를 의도할 때만 `Fixes`·`Closes`를 쓴다. 다른 리포 이슈는 `owner/repo#N`으로 적는다.
- 이유: 추적성이 생기고 의도하지 않은 이슈 자동 종료를 막는다.

### R-GIT-06 트레일러는 하네스 형식 그대로 ★★★★
- 룰: AI가 작성한 커밋에는 트레일러를 반드시 붙이고, 형식은 하네스가 안내하는 것(모델명·세션 링크 줄 포함)을 줄이거나 바꾸지 않고 그대로 쓴다. 실제로 작성에 참여한 에이전트의 트레일러만 단다.
- 이유: 작성 주체와 세션을 추적한다.

### R-GIT-07 금지 사항 ★★★★★
- 룰: 게이트가 red면 커밋하지 않는다. `--no-verify`·`--no-gpg-sign`은 쓰지 않는다. push한 커밋은 amend하거나 rebase하지 않는다. main 계열에 force push하려면 경고하고 명시적 승인을 받는다.
- 이유: 이력과 훅을 보호한다.

### R-GIT-08 main은 선형 이력 ★★★★
- 룰: 브랜치는 `git rebase main` 후 main에서 `git merge --ff-only`로 당긴다. 원격은 `git pull --rebase`로 받는다. `git config merge.ff only`·`git config pull.rebase true`를 설정하고, `.git/config`는 커밋되지 않으니 클론할 때마다 다시 설정한다.
- 이유: 워커 브랜치를 자주 머지하는 구조라 머지 커밋이 금방 쌓인다.

### R-GIT-09 rebase 충돌은 워커에게 ★★★★
- 룰: rebase 중 코드 충돌이 나면 오케스트레이터가 풀지 않고 워커에게 돌려보낸다.
- 이유: 충돌 해소도 코드 편집이다.

### R-GIT-10 rebase 뒤 게이트 재실행 ★★★★★
- 룰: 리뷰 뒤 main이 앞서 나갔다면 rebase한 브랜치에서 게이트를 다시 돌린 뒤 당긴다. 기록하는 해시는 머지 해시가 아니라 ff 뒤의 main HEAD다.
- 이유: 리뷰가 본 트리와 실제로 main에 들어가는 트리가 다르다.

## 8. 완료 보고

### R-REPORT-01 확인 방법 4종 ★★★★★
- 룰: 완료 보고 말미에 "확인 방법"을 둔다. ① 게이트 명령과 기대 출력 ② 커밋 해시·바뀐 파일·갱신한 문서(없으면 "문서 갱신 없음") ③ 작업 유형별로 직접 보는 법 — 문서는 절과 링크, CLI는 실행 예와 기대 출력, API는 `curl`, 데이터는 확인 쿼리, UI는 경로와 클릭 동선 ④ 이게 보이면 성공, 이게 보이면 실패라는 기준.
- 이유: 게이트 green이 사용자가 의도한 결과물을 보증하지는 않는다. 받는 사람이 직접 재현할 수 있어야 한다.

### R-REPORT-02 관찰할 변화가 없을 때 ★★★
- 룰: 관찰할 동작 변화가 없는 작업은 ③④를 생략하되 "관찰 가능한 변화 없음"이라고 명시한다.
- 이유: 생략도 정직하게 한다.

### R-REPORT-03 정직성 ★★★★★
- 룰: 돌리지 않은 검증은 돌렸다고 쓰지 않는다(생략했으면 사실과 이유를 적는다). 부분 완료는 막힌 이유와 함께 부분 완료로 보고한다. 목업·스텁을 "동작함"으로 보고하지 않는다.
- 이유: 에이전트 보고에서 가장 비싼 실패가 거짓 완료다.

### R-REPORT-04 배포까지 묻지 않고 ★★★ [personal] [outward] (v2 변경)
- 룰: 리뷰와 머지가 끝난 작업은 배포와 배포 후 검증까지 묻지 않고 진행한다. 운영 배포까지 마쳤으면 git push도 에이전트가 한다(R-GIT-02). 배포 절차 자체는 리포마다 정한다.
- 이유: 승인 왕복을 없앤다.

## 9. 문서·지식

### R-DOC-01 진입 파일은 인덱스만 ★★★★★ [vault]
- 룰: `AGENTS.md`(또는 `CLAUDE.md`)에는 인덱스와 레이아웃 규약만 두고, 규칙 본문은 `docs/`의 규칙 문서에 둔다. 손으로 유지하며 `deepinit` 같은 도구로 자동 재생성하지 않는다.
- 이유: 정본이 하나가 되고, 덮어써서 정책이 사라지는 일을 막는다.

### R-DOC-02 ADR에는 확정된 결정만 ★★★★★ [vault]
- 룰: 확정된 결정만 ADR로 올리고, 계획서의 채택안을 확정된 결정처럼 쓰지 않는다. 결정을 뒤집으면 새 ADR을 쓰고 이전 ADR frontmatter에 `superseded_by`를 단다(본문은 지우지 않음).
- 이유: 제안과 결정이 섞이지 않고 이력이 남는다.

### R-DOC-03 트리거가 생기면 문서부터 ★★★★ [vault]
- 룰: 결정 확정, 함정·오탐 발견(해당 규칙 문서의 함정 절), 조사·실측(조사 노트 → 굳으면 ADR로 승격하고 원본은 근거로 남김), 새 문서(인덱스에 한 줄), 새 디렉토리(레이아웃 표), 게이트 도입, 이슈 종료가 생기면 해당 문서를 갱신한 뒤에 완료 보고를 한다.
- 이유: 문서가 실제와 어긋나면 다음 세션이 낡은 사실을 근거로 잘못 판단한다.

### R-DOC-04 덧붙이지 말고 고친다 ★★★★★
- 룰: 뒤집힌 사실은 지우고 고친다(이력이 필요하면 ADR로). 같은 사실은 한 곳에만 쓰고 다른 곳에서는 링크한다. 모르는 것은 모른다고 쓴다 — 빈칸이 허구보다 낫다.
- 이유: 어느 문장이 정본인지 헷갈리지 않고, 미확인 사실이 정본으로 굳지 않는다.

### R-DOC-05 구조는 표로 관리 ★★★ [vault]
- 룰: 디렉토리 레이아웃 표를 두고, 표에 없는 디렉토리는 만들기 전에 묻고 만든 뒤 표에 한 줄 추가한다. 루트에는 설정 파일만 둔다. 채울 사실이 없는 문서·폴더는 미리 만들지 않는다.
- 이유: 구조가 무질서하게 늘지 않고, 빈 틀이 허구로 채워지지 않는다.

### R-DOC-06 데이터는 출처와 시점을 ★★★★
- 룰: 데이터 파일 인덱스(README)를 두고, 파일을 열기 전에 먼저 보며, 파일을 추가·삭제하면 한 줄 갱신한다. 출처와 시점은 파일 안에 적는다. 지표 정의(분모·기간·상태·단가)를 바꿀 때는 계산 전에 명시한다.
- 이유: 분모가 바뀐 줄 모르고 수치를 비교한 사고가 있었다.

### R-DOC-07 문서 작업 순서와 윤문 ★★★★ [ko]
- 룰: 문서는 초안 → 사실 검토 → `/humanize-korean` 윤문 → 린터 → 완료 보고 순서로 쓴다. 윤문 뒤 원문과 diff를 확인해 수치·고유명사·인용·frontmatter·표·코드·링크가 그대로인지 보고, 의미가 바뀐 구간은 되돌린다. 보고에 "윤문 완료(경로)"를 적고, 안 했으면 이유를 쓴다. 규칙·템플릿 문서, 코드·표 위주 문서, 한 줄 갱신, 사용자가 직접 쓴 문서는 윤문하지 않는다.
- 이유: AI 문체를 걷어내되 내용은 바꾸지 않는다.

### R-DOC-08 frontmatter와 표기 ★★★ [vault] [ko]
- 룰: `docs/**/*.md` 새 문서에는 frontmatter(`title`·`status: draft|review|final`)를 단다. `updated:`는 실질적으로 편집한 날에만 바꾼다. 범위·근사 표기는 ASCII `~` 대신 전각 `～`로 쓰고 린터로 강제한다(리터럴 틸드는 펜스 코드블록). `.omc/**` 같은 LLM 작업 메모리는 린터·윤문 대상에서 뺀다.
- 이유: GFM·Obsidian은 홑틸드 한 쌍 `~a~`도 취소선으로 렌더한다.

### R-DOC-09 회의록은 로컬 전용 ★★★ [vault]
- 룰: 회의록 폴더는 gitignore로 로컬에만 두고 `git add`하지 않는다. 커밋물에 녹취 내용을 언급하지 않는다.
- 이유: 민감한 발언이 리포 이력에 남지 않는다.
