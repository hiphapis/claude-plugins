# common-rules — 공통 룰을 지금 리포에 병합한다

이 스킬이 하는 일은 하나다. `references/rules.md`의 공통 룰을 **지금 리포의 룰 문서에 실제 파일로** 넣는다. 스킬로만 두지 않고 리포에 써 넣는 이유는, 워커(Codex 등)가 Claude 스킬을 읽지 못하고 리포의 `AGENTS.md`와 `docs/`만 보기 때문이다.

원칙은 세 가지다.

- **리포의 기존 룰이 주인이다.** 공통 룰은 손님으로 들어간다. 기존 구조·문체·언어를 따르고, 기존 문장은 사용자가 바꾸라고 한 경우에만 고친다.
- **충돌은 에이전트가 정하지 않는다.** 기존 룰과 공통 룰이 서로 다른 행동을 요구하면 반드시 사용자에게 묻는다. 물을 수 없는 환경이면 반영하지 말고 "미결정"으로 남긴다.
- **결정은 기록한다.** 적용한 버전과 충돌 결정을 리포에 남겨서, 다음 실행 때 같은 질문을 되풀이하지 않는다.

## 절차

### 1. 사전 점검

- git 리포인지, 작업 트리가 깨끗한지 확인한다. 미커밋 변경이 있으면 알리고 계속할지 묻는다. 병합 결과가 남의 변경과 섞이면 되돌리기 어려워지기 때문이다.
- `references/rules.md` 머리의 버전(예: `v1`)을 확인한다.

### 2. 기존 룰을 끝까지 읽는다

아래 후보를 찾아 **본문 전체를** 읽는다. 목차나 TL;DR만 보고 판단하면 실제로 있는 룰을 "누락"으로 잘못 판정한다(이 스킬을 만들 때 실제로 겪은 실수다).

- 루트 `AGENTS.md`, `CLAUDE.md`, `.claude/CLAUDE.md`, `CONTRIBUTING.md`
- `AGENTS.md`·`CLAUDE.md`가 링크하는 규칙 문서 전부(예: `docs/06-개발규칙/*.md`, `docs/rules/*.md`)
- 이전 적용 기록: `AGENTS.md`(없으면 `CLAUDE.md`)의 `## 공통 룰 적용 기록` 절, 또는 그 절이 링크하는 기록 파일
- 글로 쓰이지 않은 **리포 관례**: 기존 문서들의 frontmatter 유무, 파일 이름 규칙, 문체, 폴더 구조. 4단계에서 기존 룰과 똑같이 대조한다

이전 적용 기록이 있으면, 기록에 있는 결정(`유지`·`제외`·`조정`)은 다시 묻지 않는다. 기록 이후에 버전이 올라가 **새로 생기거나 바뀐 룰만** 대조 대상으로 삼는다.

### 3. 전제 확인 — 범주 단위로 한 번만 묻는다

이 룰은 **Orca 사용을 기본 전제로** 한다. Orca 룰은 묻지도 따지지도 않고 대상에 넣는다.

나머지 일부 룰에는 전제 태그가 붙어 있다. 근거는 **리포 자체**(파일·원격·기존 룰)에서만 찾는다. 환경변수는 실행한 세션에서 물려받은 값일 수 있으니 근거로 쓰지 않는다. 근거가 없는 범주만 사용자에게 묻고, 여러 범주를 한 질문에 묶는다(multiSelect).

| 태그 | 근거로 보는 것 |
|---|---|
| `[gh]` | 원격이 github.com이거나(`git remote -v`), 기존 룰에 GitHub 이슈·`gh` 사용이 적혀 있음 |
| `[vault]` | `docs/` 아래에 md 문서 체계(번호 폴더, 규칙 문서, ADR 등)가 있음 |
| `[ko]` | 리포 문서가 주로 한국어임 |
| `[personal]` | 리포를 혼자 쓴다는 근거(README의 "개인 프로젝트" 등). 다른 사람과 같이 쓰는 리포면 넣지 않는 편이 맞다 |

"해당 없음"과 "미결정(전제)"은 다르다. **반대 근거가 있으면** 해당 없음이다(예: 원격이 GitLab, 리포가 영어 문서뿐, README에 팀 프로젝트라고 적힘). 근거가 **아예 없으면**(원격이 비어 있음, `docs/` 폴더가 없음) 묻고, 물을 수 없으면 미결정(전제)이다. 근거끼리 엇갈리면(원격은 GitLab인데 기존 룰에는 GitHub 이슈라고 적힘) 한쪽을 고르지 말고 묻는다. 다만 **대조는 전제와 무관하게 먼저 한다.** 기존 룰에 같은 내용이 이미 있으면 전제와 상관없이 "동일"이다.

### 4. 룰마다 대조한다

남은 룰 하나하나를 기존 룰 전체와 **의미로** 비교해 네 가지 중 하나로 판정한다. 단어가 달라도 같은 행동을 요구하면 같은 룰이다.

| 판정 | 기준 | 처리 |
|---|---|---|
| **동일** | 기존 룰이 같은 행동을 요구한다 | 건드리지 않는다 |
| **보강** | 기존 룰과 공통 룰을 **동시에 지킬 수 있지만**, 공통 룰에 더 있는 내용이 있다. 공통 룰이 더 엄격하기만 한 경우(예: 기존 "`pnpm test` 통과", 공통 "JSON 결과로 skipped까지 0")도 보강이다 | 빠진 부분만 기존 문장 옆에 덧붙인다(묻지 않음) |
| **누락** | 대응하는 기존 룰이 없다 | 추가한다(묻지 않음) |
| **충돌** | 두 룰을 **동시에 지킬 수 없다.** 한쪽을 따르면 다른 쪽을 어기게 된다(예: 기존 "한두 줄은 직접 수정" ↔ 공통 "한 줄도 안 됨", 기존 "push는 사용자" ↔ 공통 "문서 커밋은 자동 push") | 사용자에게 묻는다 |

판정 기준은 한 문장이다. **"두 룰을 동시에 지킬 수 있는가?"** 있으면 보강, 없으면 충돌이다. 이 질문에 답할 수 없을 만큼 애매하면 충돌로 분류한다. 보강으로 잘못 넣으면 사용자 모르게 기존 룰의 뜻이 바뀌기 때문이다.

판정을 다듬는 규칙 네 가지가 더 있다.

- **리포 관례도 기존 룰이다.** frontmatter 유무, 파일 이름 규칙처럼 글로 쓰이지 않았어도 기존 파일들이 일관되게 따르는 형식은 사실상의 룰로 보고 대조한다. 공통 룰이 그 관례를 바꾸면 충돌이다(예: 기존 문서에 frontmatter가 없는데 R-DOC-08은 붙이라고 함). 관례를 따르는 게 보통은 맞지만, 사용자가 **그 관례를 바꾸려고** 이 스킬을 돌렸을 수도 있으니 에이전트가 정하지 않는다.
- **룰의 일부만 충돌하면 쪼갠다.** 동시에 지킬 수 있는 부분은 보강·누락으로 넣고, 충돌하는 부분만 묻는다. ID는 `R-GIT-02(일부)`처럼 표시하고, 적용 기록에도 어느 부분이 남았는지 적는다.
- **종속.** 충돌한 룰에 기대는 다른 룰(예: 직접 수정 범위가 충돌하면, 그 범위를 전제로 한 종결 조건 룰)은 함께 보류하고 "종속: <원인 룰 ID>"로 표시한다. 원인이 여럿이면 `종속: R-ROLE-01, R-GIT-08`처럼 모두 적는다. 원인 충돌이 결정되면 함께 처리한다. 기존 룰의 예외 범위를 좁히기만 하는 룰도 그 예외와 충돌한 룰에 종속된 것으로 본다.
- **리포 밖으로 나가는 룰은 누락이어도 묻는다.** `rules.md`에서 `[outward]` 표시가 붙은 룰(자동 push, 이슈 자동 종료, 묻지 않는 배포 등)은 기존 룰에 대응 문장이 없어도 넣기 전에 확인한다. 리포를 다른 사람과 같이 쓰면 영향이 리포 밖까지 가기 때문이다. 일부 충돌과 똑같이 **리포 밖으로 나가는 부분만** 묻고, 나머지 부분(예: R-GIT-02의 "묻지 않고 커밋")은 넣는다.
- **전제 태그가 둘 이상이면 모두 충족해야 한다.** 일부 전제만 충족된 룰은 미결정(전제)으로 남기되, 기존 룰과 같은 부분이 있으면 그 부분은 동일로 본다.

공통 룰을 넣는 순간 **기존 상태가 그 룰을 어기게 되는** 경우도 있다(예: R-DOC-01 "`AGENTS.md`에는 인덱스만"을 넣었는데 기존 `AGENTS.md`에 룰 본문이 있음). 이때 룰은 넣되 기존 문장을 옮기지는 않고, 보고서의 「정리가 필요한 기존 상태」 목록에 올린다.

### 5. 대조표를 보여 주고 충돌을 묻는다

먼저 요약을 보여 준다: 동일 N · 보강 N · 누락 N · 충돌 N · 해당 없음 N. 그다음 충돌(관례 충돌, 일부 충돌, `[outward]` 확인 포함)을 AskUserQuestion으로 묻는다(한 번에 최대 4개, 별점 높은 순). 같은 기존 문장에서 생긴 충돌과 그 종속 룰은 한 질문으로 묶는다. `[outward]` 확인은 "넣기 / 넣지 않기(이 리포의 예외로 기록)"를 고르게 한다.

질문은 대화창 없이도 읽히게 쓴다. 질문 본문에 **기존 문장(파일:줄)**과 **공통 룰 문장**을 둘 다 인용한다. 선택지는 다음 셋이다.

- **공통 룰로 교체** — 기존 문장을 공통 룰에 맞게 그 자리에서 고친다
- **기존 유지** — 이 리포의 예외로 기록한다
- **조정** — 사용자가 직접 문구를 정한다(Other 입력)

AskUserQuestion을 쓸 수 없는 환경이면 충돌을 하나도 반영하지 않는다. 대신 각 충돌을 "미결정"으로 적용 기록에 남기고 보고서에 목록으로 낸다. 다른 질문도 마찬가지다 — 아래 「물을 수 없을 때」를 따른다.

### 6. 배치를 정한다

`references/layout.md`의 배치 규칙을 따른다. 요약하면 다음과 같다.

- 리포에 룰 문서 체계가 있으면 **그 체계 안에서** 주제가 맞는 파일에 넣는다. 맞는 파일이 없을 때만 같은 폴더에 새 파일을 만들고, 인덱스(`AGENTS.md` 등)에 한 줄 추가한다.
- 체계가 없으면 `layout.md`의 기본 구조를 제안하고, 만들기 전에 사용자에게 한 번 묻는다. 거절하면 `AGENTS.md`(없으면 `CLAUDE.md`)에 섹션으로 넣는다.

### 7. 쓴다

- 기존 문체와 언어를 따른다. 공통 룰 문장을 그대로 붙여 넣지 말고, 주변 문장과 같은 톤으로 다듬는다. 뜻은 바꾸지 않는다.
- 같은 사실을 두 곳에 쓰지 않는다. 이미 다른 파일에 있는 내용이면 링크한다.
- "공통 룰로 교체"로 결정된 충돌은 **덧붙이지 말고 그 자리에서 고친다.** 낡은 문장과 새 문장이 함께 남으면 어느 쪽이 정본인지 알 수 없다.
- 리포마다 값이 다른 자리(게이트 명령, 원격 이름, 디렉토리 표 등)는 지어내지 않는다. 리포에서 확인할 수 없으면 `<미정: 게이트 명령>`처럼 표시하고 보고서에 목록으로 낸다. 빈칸이 허구보다 낫다.
- frontmatter·파일 이름·문체 같은 형식은 4단계 판정 결과를 따른다. 공통 룰과 관례가 같거나 사용자가 관례 유지를 골랐으면 관례대로, 공통 룰을 골랐으면 공통 룰대로 쓴다. 아직 결정되지 않았으면(미결정) 관례대로 쓴다. frontmatter를 쓰는 리포에서는 고친 파일의 `updated:`를 오늘 날짜로 바꾼다.
- 넣거나 보강한 문장 끝에 룰 ID를 HTML 주석으로 단다: `… 경로를 명시해서 add 한다. <!-- R-GIT-03 -->`. 렌더된 화면에는 보이지 않지만, 다음 버전을 적용할 때 어느 문장이 어느 룰에서 왔는지 바로 찾을 수 있다. 사용자가 쓴 기존 문장이 "동일"로 판정된 경우에도 그 문장 끝에 ID를 달고, 일부만 같으면 `<!-- R-BASE-04(일부) -->`로 단다. 충돌로 남긴 기존 문장에는 달지 않는다(그 문장은 아직 공통 룰이 아니다).
- R-ROLE-04(현재 워커 설정)는 역할 룰이 들어가는 파일·절의 맨 위에 둔다.

### 8. 적용 기록을 남긴다

기본 위치는 `AGENTS.md`(없으면 `CLAUDE.md`) 맨 끝이다. 이미 있으면 그 자리에서 갱신한다.

다만 R-DOC-01("`AGENTS.md`에는 인덱스만")을 이 리포에 넣기로 했다면 기본 위치가 그 룰과 부딪힌다. 이때는 위치를 사용자에게 묻는다 — `AGENTS.md` 끝에 둘지, 규칙 폴더 안의 별도 파일(예: `docs/rules/common-rules-log.md`)에 두고 `AGENTS.md`에는 링크 한 줄만 둘지. 물을 수 없으면 기본 위치에 쓰고 보고서에 적는다.

```markdown
## 공통 룰 적용 기록

- 버전: common-rules v1 (YYYY-MM-DD 적용)
- 해당 없음: [gh] — 원격이 GitLab
- 기존 유지: R-GIT-08 — 이 리포는 머지 커밋을 쓴다(사용자 결정 YYYY-MM-DD)
- 조정: R-ROLE-01 — "<사용자가 정한 문구 요약>"
- 미결정(충돌): R-GIT-02(일부) — 자동 push 부분이 AGENTS.md:12 "push는 사용자가 한다"와 충돌. "묻지 않고 커밋" 부분은 반영함. 비대화형 실행이라 묻지 못함
- 미결정(관례 충돌): R-DOC-08 — 기존 docs/rules/*.md에 frontmatter가 없음. 관례대로 두었음
- 미결정(outward): R-ISSUE-08 — 리포 밖 행동이라 확인 필요
- 미결정(충돌·종속): R-ROLE-07 — 종속: R-ROLE-01
- 미결정(전제): [vault] — docs/ 체계 근거 없음. 해당 룰: R-DOC-01·02·…
```

"동일·보강·누락"으로 처리한 룰은 하나하나 적지 않는다. 버전만으로 알 수 있다.

### 9. 검증하고 보고한다

- 쓴 파일을 다시 읽어, 같은 룰이 두 번 들어가지 않았는지, 충돌이 결정과 다르게 반영되지 않았는지 확인한다.
- 리포에 문서 린터가 있으면 돌린다(예: `node scripts/lint-md-tilde.mjs`).
- 커밋은 리포의 git 룰을 따른다. 리포 룰로 판단할 수 없으면 커밋하지 말고 사용자에게 맡긴다.

보고서 형식:

```markdown
## 공통 룰 적용 결과 (common-rules v1)

| 판정 | 건수 | 룰 ID |
|---|---|---|
| 동일 | | |
| 보강 | | |
| 누락 → 추가 | | |
| 충돌 → 교체/유지/조정 | | |
| 미결정(충돌·관례·일부·종속) | | |
| 미결정(outward) | | |
| 미결정(전제) | | |
| 해당 없음(반대 근거 있음) | | |

미결정 사유가 여럿인 룰(예: outward이면서 전제 미결정)은 표의 한 행에만 세고, 적용 기록에 사유를 모두 적는다.

바뀐 파일: <경로 목록>
미정 값: <`<미정: …>` 목록, 없으면 "없음">
정리가 필요한 기존 상태: <새 룰을 이미 어기고 있는 기존 문장·구조, 없으면 "없음">
확인 방법: `git diff`로 변경을 보고, `AGENTS.md`의 「공통 룰 적용 기록」 절에서 결정을 확인한다.
```

## 물을 수 없을 때 (비대화형 실행)

서브에이전트나 비대화형 실행처럼 AskUserQuestion을 쓸 수 없으면, 질문이 필요한 자리마다 **가장 덜 침습적인 쪽**을 고르고 그 사실을 기록한다. 사용자가 나중에 다시 실행해서 결정할 수 있게 하는 것이 목적이다.

| 원래 묻는 것 | 물을 수 없을 때 |
|---|---|
| 미커밋 변경이 있는데 계속할지 | 중단하고 보고한다 |
| 근거 없는 전제 범주를 넣을지 | 넣지 않는다. 적용 기록에 "미결정(전제)"으로 남긴다 |
| 충돌 처리(관례 충돌 포함) | 반영하지 않고 기존 룰·관례를 그대로 둔다. "미결정(충돌)"·"미결정(관례 충돌)"로 남기고, 종속 룰도 함께 남긴다. 일부 충돌이면 지킬 수 있는 부분만 넣는다 |
| `[outward]` 룰을 넣을지 | 리포 밖으로 나가는 부분만 넣지 않고 "미결정(outward)"으로 남긴다. 나머지 부분은 넣는다 |
| 적용 기록 위치(R-DOC-01과 부딪힐 때) | `AGENTS.md` 끝에 쓰고 보고서에 적는다 |
| 전제 근거가 엇갈릴 때 | 넣지 않는다. "미결정(전제)"으로 남기고 엇갈린 근거를 적는다 |
| 새 문서 구조(새 폴더 체계)를 만들지 | 만들지 않는다. `AGENTS.md`(없으면 `CLAUDE.md`, 둘 다 없으면 새 `AGENTS.md`)에 절로 넣는다. 이미 있는 규칙 폴더 안에 새 파일을 만드는 것은 질문 대상이 아니므로 그대로 한다(`layout.md` §1) |

## 공통 룰 자체를 고칠 때

룰을 추가·변경하려면 `references/rules.md`를 고치고 머리의 버전을 올린다. 바뀐 룰의 ID 옆에 `(v2 변경)`처럼 표시해 두면, 이미 적용한 리포에서 다시 실행할 때 그 룰만 대조한다.
