# common-rules — 공통 룰을 지금 리포에 병합한다

이 스킬이 하는 일은 하나다. `references/rules.md`의 공통 룰을 **지금 리포의 룰 문서에 실제 파일로** 넣는다. 스킬로만 두지 않고 리포에 써 넣는 이유는, 에이전트가 읽는 것이 스킬 본문이 아니라 리포의 문서이기 때문이다. 세션을 시작할 때 진입 파일(`AGENTS.md`·`CLAUDE.md`)을 자동으로 읽고, 거기 인덱스가 가리키는 `docs/` 문서는 필요할 때 연다. Orca가 띄운 워커도 마찬가지이고, Codex 같은 다른 에이전트는 Claude 스킬을 아예 읽지 못한다.

원칙은 세 가지다.

- **리포의 기존 룰이 주인이다.** 공통 룰은 손님으로 들어간다. 기존 구조·문체·언어를 따르고, 기존 문장은 사용자가 바꾸라고 한 경우에만 고친다.
- **충돌은 에이전트가 정하지 않는다.** 기존 룰과 공통 룰이 서로 다른 행동을 요구하면 반드시 사용자에게 묻는다. 물을 수 없는 환경이면 반영하지 말고 "미결정"으로 남긴다.
- **결정은 기록한다.** 적용한 버전과 충돌 결정을 리포에 남겨서, 다음 실행 때 같은 질문을 되풀이하지 않는다.

## 절차

### 1. 사전 점검

- git 리포인지, 작업 트리가 깨끗한지 확인한다. 미커밋 변경이 있으면 알리고 계속할지 묻는다. 병합 결과가 남의 변경과 섞이면 되돌리기 어려워지기 때문이다.
- `references/rules.md` 머리의 버전(예: `v1`)을 확인한다. 제목에 `(vN 삭제)`가 붙은 룰은 카탈로그에서 지운 룰이다. 이 룰은 어느 단계에서도 넣거나 판정할 대상이 아니다(전제가 새로 충족됐을 때의 재판정 포함). 다시 실행할 때 「삭제된 룰」 절차로 걷어 내기만 한다.
- `command -v orca`로 Orca가 있는지 본다. Orca는 카탈로그 전체의 전제라, 없으면 "Orca 없이도 룰을 넣을지(다른 머신에서 Orca로 쓸 리포인지)"를 먼저 한 번 묻는다. 중단을 고르면 아무것도 쓰지 않고 끝낸다.

### 2. 기존 룰을 끝까지 읽는다

아래 후보를 찾아 **본문 전체를** 읽는다. 목차나 TL;DR만 보고 판단하면 실제로 있는 룰을 "누락"으로 잘못 판정한다(이 스킬을 만들 때 실제로 겪은 실수다).

- 루트 `AGENTS.md`, `CLAUDE.md`, `.claude/CLAUDE.md`, `CONTRIBUTING.md`
- `.claude/rules/*.md`. Claude Code가 자동으로 읽는 룰 파일이므로 기존 룰로 대조한다
- `AGENTS.md`·`CLAUDE.md`가 링크하는 규칙 문서 전부(예: `docs/06-개발규칙/*.md`, `docs/rules/*.md`)
- 하위 디렉토리의 `AGENTS.md`·`CLAUDE.md`(모노레포의 패키지별 룰). 그 디렉토리에만 적용되는 룰이라 **충돌을 찾는 데만** 쓴다. 공통 룰과 같은 문장이 있어도 "동일"로 치지 않고 루트 쪽에 넣는다. 하위 문서는 고치지 않고 ID 주석도 달지 않으며, 공통 룰과 충돌하는 문장은 보고서의 「정리가 필요한 상태」에 올린다
- 이전 적용 기록: `AGENTS.md`(없으면 `CLAUDE.md`)의 `## 공통 룰 적용 기록` 절, 또는 "공통 룰 적용 기록"이라는 이름으로 링크된 기록 파일
- 글로 쓰이지 않은 **리포 관례**: 기존 문서들의 frontmatter 유무, 파일 이름 규칙, 문체, 폴더 구조. 4단계에서 기존 룰과 똑같이 대조한다

이전 적용 기록이 있으면 처음부터 다시 대조하지 않고 아래 「다시 실행할 때」를 따른다.

### 3. 전제 확인 — 범주 단위로 한 번만 묻는다

이 룰은 **Orca 사용을 기본 전제로** 한다. Orca 룰은 묻지도 따지지도 않고 대상에 넣는다.

나머지 일부 룰에는 전제 태그가 붙어 있다. 근거는 **리포 자체**(파일·원격·기존 룰)에서만 찾는다. 환경변수는 실행한 세션에서 물려받은 값일 수 있으니 근거로 쓰지 않는다. 근거가 없는 범주만 사용자에게 묻고, 여러 범주를 한 질문에 묶는다(multiSelect). 사용자가 넣지 않겠다고 답한 범주는 적용 기록에 `해당 없음: [태그] — 사용자 결정`으로 남긴다.

| 태그 | 근거로 보는 것 |
|---|---|
| `[gh]` | 원격이 github.com이거나(`git remote -v`), 기존 룰에 GitHub 이슈·`gh` 사용이 적혀 있음 |
| `[vault]` | `docs/` 아래에 md 문서 체계(번호 폴더, 규칙 문서, ADR 등)가 있음 |
| `[ko]` | 리포 문서가 주로 한국어임 |
| `[personal]` | 리포를 혼자 쓴다는 근거(README의 "개인 프로젝트" 등). 다른 사람과 같이 쓰는 리포면 넣지 않는 편이 맞다 |

"해당 없음"과 "미결정(전제)"은 다르다. **반대 근거가 있으면** 해당 없음이다(예: 원격이 GitLab, 리포가 영어 문서뿐, README에 팀 프로젝트라고 적힘). 근거가 **아예 없으면**(원격이 비어 있음, `docs/` 폴더가 없음) 묻고, 물을 수 없으면 미결정(전제)이다. 근거끼리 엇갈리면(원격은 GitLab인데 기존 룰에는 GitHub 이슈라고 적힘) 한쪽을 고르지 말고 묻는다. 다만 **대조는 전제와 무관하게 먼저 한다.** 기존 룰에 같은 내용이 이미 있으면 전제와 상관없이 "동일"이다.

**도구도 확인한다.** `rules.md` 머리의 「도구 의존」 표로 Orca 외 도구(`gh`, worktree-teardown, `ccg`, `ego-browser`, humanize-korean)가 있는지 본다. 표에 최소 버전이 적힌 도구는 버전도 확인하고(플러그인은 `claude plugin list`), 낮으면 없는 도구와 똑같이 다루되 적용 기록에는 "도구 없음(버전 낮음)"으로 적는다. 전제 태그로 이미 빠진 룰의 도구는 보지 않는다. 도구가 없다는 건 **이 머신**의 사실이지 리포의 사실이 아니므로(리포는 다른 머신에서도 쓰인다), 도구가 없다고 룰을 빼지 않는다. 없는 도구마다 다음 중 하나를 묻고, 전제 질문과 한 번에 묶는다.

- **설치하고 넣기** — 표의 「설치」 칸에 명령이 있는 도구만 고를 수 있다. 사용자가 고른 뒤에만 그 명령을 실행하고, 실패하면 "룰만 넣기"로 처리하고 실패 출력을 보고한다. 설치 뒤 남는 일(세션 재시작, `gh auth login`, Codex·Gemini CLI 설치)은 보고서의 「남은 할 일」에 적는다
- **룰만 넣기(나중에 설치)** — 룰은 넣고 적용 기록에 "도구 없음"으로 남긴다. 「설치」 칸이 "안내만"인 도구는 이 선택지와 빼기만 주고, 안내 링크를 보고서에 적는다
- **빼기** — 이 리포의 예외로 기록한다

설치는 이 머신을 바꾸는 행동이라 사용자가 고르지 않으면 하지 않는다. 넣은 룰은 실행 시점에 R-BASE-10(도구가 없으면 우회하지 않고 묻는다)이 지킨다.

### 4. 룰마다 대조한다

남은 룰 하나하나를 기존 룰 전체와 **의미로** 비교해 네 가지 중 하나로 판정한다. 단어가 달라도 같은 행동을 요구하면 같은 룰이다.

| 판정 | 기준 | 처리 |
|---|---|---|
| **동일** | 기존 룰이 같은 행동을 요구한다 | 문장은 바꾸지 않는다. 끝에 ID 주석만 단다(7단계) |
| **보강** | 기존 룰과 공통 룰을 **동시에 지킬 수 있지만**, 공통 룰에 더 있는 내용이 있다. 공통 룰이 더 엄격하기만 한 경우(예: 기존 "`pnpm test` 통과", 공통 "JSON 결과로 skipped까지 0")도 보강이다 | 빠진 부분만 기존 문장 옆에 덧붙인다(묻지 않음) |
| **누락** | 대응하는 기존 룰이 없다 | 추가한다(묻지 않음) |
| **충돌** | 두 룰을 **동시에 지킬 수 없다.** 한쪽을 따르면 다른 쪽을 어기게 된다(예: 기존 "main에는 머지 커밋을 남긴다" ↔ 공통 "ff-only 선형 이력", 기존 "push는 사용자" ↔ 공통 "문서 커밋은 자동 push"). 한쪽이 **명시적으로 허용·면제한 것을 다른 쪽이 금지·요구**하는 경우도 충돌이다(예: 기존 "한두 줄은 직접 고쳐도 된다" ↔ 공통 "한 줄도 안 됨") | 사용자에게 묻는다 |

판정 기준은 한 문장이다. **"두 룰을 동시에 지킬 수 있는가?"** 있으면 보강, 없으면 충돌이다. 이 질문에 답할 수 없을 만큼 애매하면 충돌로 분류한다. 보강으로 잘못 넣으면 사용자 모르게 기존 룰의 뜻이 바뀌기 때문이다.

한 가지만 따로 본다. 한쪽 룰이 어떤 행동을 **명시적으로 허용하거나 면제한** 것을 다른 쪽이 금지하거나 요구하면, 더 엄격한 쪽만 따르면 둘 다 지킬 수 있어 보여도 충돌이다. 방향은 상관없다. 기존 룰이 일부러 열어 둔 것을 닫는 일이거나(기존 "한두 줄은 직접 고쳐도 된다" ↔ 공통 "한 줄도 안 됨"), 기존 룰이 일부러 막아 둔 것을 여는 일(기존 "문서 수정도 이슈부터 만든다" ↔ 공통 "문서만 고치는 작업에는 이슈가 필요 없다")이기 때문이다. 어느 쪽도 허용이나 면제를 말하지 않고 공통 룰이 요구를 더하기만 하면 보강이다.

판정을 다듬는 규칙 다섯 가지가 더 있다.

- **리포 관례도 기존 룰이다.** frontmatter 유무, 파일 이름 규칙처럼 글로 쓰이지 않았어도 기존 파일들이 일관되게 따르는 형식은 사실상의 룰로 보고 대조한다. 공통 룰이 그 관례를 바꾸면 충돌이다(예: 기존 문서에 frontmatter가 없는데 R-DOC-08은 붙이라고 함). 관례를 따르는 게 보통은 맞지만, 사용자가 **그 관례를 바꾸려고** 이 스킬을 돌렸을 수도 있으니 에이전트가 정하지 않는다.
- **룰의 일부만 충돌하면 쪼갠다.** 동시에 지킬 수 있는 부분은 보강·누락으로 넣고, 충돌하는 부분만 묻는다. ID는 `R-GIT-02(일부)`처럼 표시하고, 적용 기록에도 어느 부분이 남았는지 적는다.
- **종속.** 충돌한 룰에 기대는 다른 룰(예: 직접 수정 범위가 충돌하면, 그 범위를 전제로 한 종결 조건 룰)은 함께 보류하고 "종속: <원인 룰 ID>"로 표시한다. 원인이 여럿이면 `종속: R-ROLE-01, R-GIT-08`처럼 모두 적는다. 원인 충돌이 결정되면 함께 처리한다. 기존 룰의 예외 범위를 좁히기만 하는 룰도 그 예외와 충돌한 룰에 종속된 것으로 본다.
- **리포 밖으로 나가는 룰은 누락이어도 묻는다.** `rules.md`에서 `[outward]` 표시가 붙은 룰(자동 push, 이슈 자동 종료, 묻지 않는 배포 등)은 기존 룰에 대응 문장이 없어도 넣기 전에 확인한다. 리포를 다른 사람과 같이 쓰면 영향이 리포 밖까지 가기 때문이다. 일부 충돌과 똑같이 **리포 밖으로 나가는 부분만** 묻고, 나머지 부분(예: R-GIT-02의 "묻지 않고 커밋")은 넣는다.
- **전제 태그가 둘 이상이면 모두 충족해야 한다.** 일부 전제만 충족된 룰은 미결정(전제)으로 남기되, 기존 룰과 같은 부분이 있으면 그 부분은 동일로 본다.

공통 룰을 넣는 순간 **기존 상태가 그 룰을 어기게 되는** 경우도 있다(예: R-DOC-01 "`AGENTS.md`에는 인덱스만"을 넣었는데 기존 `AGENTS.md`에 룰 본문이 있음). 이때 룰은 넣되 기존 문장을 옮기지는 않고, 보고서의 「정리가 필요한 상태」 목록에 올린다.

### 5. 대조표를 보여 주고 충돌을 묻는다

먼저 요약을 보여 준다: 동일 N · 보강 N · 누락 N · 충돌 N · 해당 없음 N(다시 실행할 때는 갱신 N·삭제 N도 함께). 그다음 충돌(관례 충돌, 일부 충돌, `[outward]` 확인 포함)을 AskUserQuestion으로 묻는다(한 번에 최대 4개, 별점 높은 순). 같은 기존 문장에서 생긴 충돌과 그 종속 룰은 한 질문으로 묶는다. `[outward]` 확인은 "넣기 / 넣지 않기(이 리포의 예외로 기록)"를 고르게 하고, 넣지 않기는 적용 기록에 `제외(outward)`로 남긴다.

질문은 대화창 없이도 읽히게 쓴다. 질문 본문에 **기존 문장(파일:줄)**과 **공통 룰 문장**을 둘 다 인용한다. 선택지는 다음 셋이다.

- **공통 룰로 교체** — 기존 문장을 공통 룰에 맞게 그 자리에서 고친다
- **기존 유지** — 이 리포의 예외로 기록한다
- **조정** — 사용자가 직접 문구를 정한다(Other 입력)

AskUserQuestion을 쓸 수 없는 환경이면 충돌을 하나도 반영하지 않는다. 대신 각 충돌을 "미결정"으로 적용 기록에 남기고 보고서에 목록으로 낸다. 다른 질문도 마찬가지다 — 아래 「물을 수 없을 때」를 따른다.

### 6. 배치를 정한다

`references/layout.md`의 배치 규칙을 따른다. 요약하면 다음과 같다.

- 리포에 룰 문서 체계가 있으면 **그 체계 안에서** 주제가 맞는 파일에 넣는다. 맞는 파일이 없을 때만 같은 폴더에 새 파일을 만들고, 인덱스(`AGENTS.md` 등)에 한 줄 추가한다.
- 체계가 없으면 `layout.md`의 기본 구조를 제안하고, 만들기 전에 사용자에게 한 번 묻는다. 거절하면 `AGENTS.md`(없으면 `CLAUDE.md`)에 섹션으로 넣는다.
- R-ROLE-12(역할 판별)는 어느 경우든 진입 파일에 직접 넣는다(`layout.md` §1). 어느 에이전트든 세션을 시작할 때 자동으로 읽는 파일은 진입 파일뿐이기 때문이다.
- 룰을 쓸 파일이 세션을 시작할 때 **실제로 읽히는지** 확인한다(`layout.md` §3). Claude Code는 `CLAUDE.md`가 있으면 `AGENTS.md`를 읽지 않으므로, `CLAUDE.md`가 `AGENTS.md`를 import하지 않는 리포에서 `AGENTS.md`에 룰을 넣으면 Claude 세션은 그 룰을 읽지 못한다. 이때 `CLAUDE.md`에 `AGENTS.md`를 import하는 줄을 넣을지 묻는다.

### 7. 쓴다

- 넣는 것은 룰 문장이다. 카탈로그의 제목·별점·전제 태그·「이유」는 넣지 않는다(판정과 질문에 쓰는 정보다). 이유가 없으면 룰을 잘못 읽게 되는 경우에만 한 구절로 덧붙인다.
- 기존 문체와 언어를 따른다. 공통 룰 문장을 그대로 붙여 넣지 말고, 주변 문장과 같은 톤으로 다듬는다. 뜻은 바꾸지 않는다.
- 같은 사실을 두 곳에 쓰지 않는다. 이미 다른 파일에 있는 내용이면 링크한다.
- "공통 룰로 교체"로 결정된 충돌은 **덧붙이지 말고 그 자리에서 고친다.** 낡은 문장과 새 문장이 함께 남으면 어느 쪽이 정본인지 알 수 없다.
- 리포마다 값이 다른 자리(게이트 명령, 원격 이름, 디렉토리 표 등)는 지어내지 않는다. 리포에서 확인할 수 없으면 `<미정: 게이트 명령>`처럼 표시하고 보고서에 목록으로 낸다. 빈칸이 허구보다 낫다.
- frontmatter·파일 이름·문체 같은 형식은 4단계 판정 결과를 따른다. 공통 룰과 관례가 같거나 사용자가 관례 유지를 골랐으면 관례대로, 공통 룰을 골랐으면 공통 룰대로 쓴다. 아직 결정되지 않았으면(미결정) 관례대로 쓴다. frontmatter를 쓰는 리포에서는 고친 파일의 `updated:`를 오늘 날짜로 바꾼다.
- 스킬이 통째로 쓴 문장 끝에 룰 ID를 HTML 주석으로 단다: `… 경로를 명시해서 add 한다. <!-- R-GIT-03 -->`. 렌더된 화면에는 보이지 않지만, 다음 버전을 적용할 때 어느 문장이 어느 룰에서 왔는지 바로 찾을 수 있다.
- 사용자가 쓴 글이 들어 있는 문장에는 ID 뒤에 `기존`을 붙인다. "동일"로 판정된 기존 문장이면 `<!-- R-GIT-07 기존 -->`, 일부만 같으면 `<!-- R-BASE-04(일부) 기존 -->`로 단다. 기존 문장 옆에 덧붙여 보강한 경우도 사용자 글이 섞인 줄이므로 `기존`을 붙인다. 다시 실행할 때 `기존` 표시가 없는 문장은 스킬이 쓴 것으로 보고 묻지 않고 고치므로, 이 표시를 빠뜨리지 않는다. 충돌로 남긴 기존 문장에는 ID를 달지 않는다(그 문장은 아직 공통 룰이 아니다).
- R-ROLE-12(역할 판별)는 진입 파일에 넣는다(6단계). R-ROLE-04(현재 워커 설정)는 역할 룰이 들어가는 파일·절의 맨 위에 둔다.

### 8. 적용 기록을 남긴다

기본 위치는 `AGENTS.md`(없으면 `CLAUDE.md`) 맨 끝이다. 이미 있으면 그 자리에서 갱신한다. 절 제목 `## 공통 룰 적용 기록`은 리포 문서가 다른 언어여도 그대로 쓴다. 다음 실행이 이 제목으로 기록을 찾기 때문이다.

다만 R-DOC-01("`AGENTS.md`에는 인덱스만")을 이 리포에 넣기로 했다면 기본 위치가 그 룰과 부딪힌다. 이때는 위치를 사용자에게 묻는다 — `AGENTS.md` 끝에 둘지, 규칙 폴더 안의 별도 파일(예: `docs/rules/common-rules-log.md`)에 두고 `AGENTS.md`에는 "공통 룰 적용 기록"이라는 이름의 링크 한 줄만 둘지. 물을 수 없으면 기본 위치에 쓰고 보고서에 적는다.

```markdown
## 공통 룰 적용 기록

- 버전: common-rules v1 (YYYY-MM-DD 적용)
- 출처 표시: 확인함(YYYY-MM-DD)
- 해당 없음: [gh] — 원격이 GitLab
- 해당 없음: [personal] — 여럿이 쓰는 리포(사용자 결정 YYYY-MM-DD)
- 기존 유지: R-GIT-08 — 이 리포는 머지 커밋을 쓴다(사용자 결정 YYYY-MM-DD)
- 기존 유지: CLAUDE.md에 `@AGENTS.md`를 넣지 않음(사용자 결정 YYYY-MM-DD)
- 조정: R-ROLE-01 — "<사용자가 정한 문구 요약>"
- 제외(outward): R-REPORT-04 — 묻지 않는 배포는 넣지 않음(사용자 결정 YYYY-MM-DD)
- 미결정(충돌): R-GIT-02(일부) — 자동 push 부분이 AGENTS.md:12 "push는 사용자가 한다"와 충돌. "묻지 않고 커밋" 부분은 반영함. 비대화형 실행이라 묻지 못함
- 미결정(관례 충돌): R-DOC-08 — 기존 docs/rules/*.md에 frontmatter가 없음. 관례대로 두었음
- 미결정(outward): R-ISSUE-08 — 리포 밖 행동이라 확인 필요
- 미결정(충돌·종속): R-ROLE-07 — 종속: R-ROLE-01
- 미결정(전제): [vault] — docs/ 체계 근거 없음. 해당 룰: R-DOC-01·02·…
- 미결정(재확인): R-GIT-08 — 새 버전에서 바뀐 부분이 "기존 유지" 결정과 겹침. 비대화형 실행이라 묻지 못함
- 미결정(삭제): <지운 룰 ID> — 카탈로그에서 지운 룰인데 AGENTS.md:40이 `조정` 문구라 지우지 못함. 비대화형 실행이라 묻지 못함
- 미결정(읽힘): CLAUDE.md가 AGENTS.md를 import하지 않아 Claude 세션이 룰을 읽지 못함. `@AGENTS.md`를 넣을지 묻지 못함
- 도구 없음: oh-my-claudecode `ccg` — 적용한 머신에 없음. R-ROLE-09는 넣었음(사용자 결정 YYYY-MM-DD)
- 도구 없음: `gh` — 적용한 머신에 없음. `[gh]` 룰은 넣었음(비대화형 실행이라 묻지 못함)
- 제외(도구): R-BASE-05 — `ego-browser`를 쓰지 않는 리포(사용자 결정 YYYY-MM-DD)
```

"동일·보강·누락"으로 처리한 룰은 하나하나 적지 않는다. 버전만으로 알 수 있다. `출처 표시: 확인함`은 리포의 모든 ID 주석에 `기존` 표시가 맞게 달려 있다는 뜻이다. 처음 적용할 때는 7단계에서 표시를 달았으므로 바로 남긴다.

### 9. 검증하고 보고한다

- 쓴 파일을 다시 읽어, 같은 룰이 두 번 들어가지 않았는지, 충돌이 결정과 다르게 반영되지 않았는지 확인한다.
- 리포에 문서 린터가 있으면 돌린다(예: `node scripts/lint-md-tilde.mjs`).
- 진입 파일(`AGENTS.md`·`CLAUDE.md`)에 룰 본문을 직접 넣었으면 그 파일의 크기를 본다. 진입 파일은 매 세션과 매 워커가 통째로 읽고, Codex는 기본으로 32KiB까지만 읽는다. 32KiB를 넘으면 보고서의 「정리가 필요한 상태」에 적는다.
- 커밋할지는 **이 실행 전부터 리포에 있던** git 룰로 정한다. 이번에 넣은 룰은 자기 자신을 커밋하는 근거가 되지 못한다. 기존 룰이 묻지 않는 커밋을 허용하면 그 범위에서 커밋하되, 규칙 문서 검토처럼 커밋 전에 거칠 절차가 기존 룰에 있으면 먼저 거친다. 기존 룰로 판단할 수 없으면 커밋하지 말고 사용자에게 맡긴다.

보고서 형식:

```markdown
## 공통 룰 적용 결과 (common-rules v1)

| 판정 | 건수 | 룰 ID |
|---|---|---|
| 동일 | | |
| 보강 | | |
| 누락 → 추가 | | |
| 갱신(바뀐 룰을 그 자리에서 반영) | | |
| 삭제(지운 룰의 문장을 걷어 냄) | | |
| 충돌 → 교체/유지/조정 | | |
| 미결정(충돌·관례·일부·종속·재확인) | | |
| 미결정(outward) | | |
| 미결정(전제) | | |
| 해당 없음(반대 근거 또는 사용자 결정) | | |
| 제외(outward) | | |
| 제외(도구) | | |

미결정 사유가 여럿인 룰(예: outward이면서 전제 미결정)은 표의 한 행에만 세고, 적용 기록에 사유를 모두 적는다.

도구 없음 경고: <이 머신에 없거나 버전이 낮은 도구와 그 도구에 기대는 룰 ID, 없으면 "없음">. 룰은 넣었으니 쓰기 전에 설치해야 한다.
설치한 도구: <설치 명령과 결과, 없으면 "없음">
남은 할 일: <세션 재시작, `gh auth login`, 안내만 한 도구의 설치 링크 등, 없으면 "없음">

바뀐 파일: <경로 목록>
갱신한 문장: <다시 실행하면서 그 자리에서 고친 문장의 `파일:줄`과 룰 ID, 없으면 "없음">
지운 문장: <삭제된 룰 때문에 지운 문장이나 ID를 뺀 주석의 `파일:줄`과 룰 ID, 없으면 "없음">
읽히지 않는 룰: <룰을 쓴 파일을 세션 시작 때 읽지 못하는 에이전트와 고치는 방법(`layout.md` §3), 없으면 "없음">
미정 값: <`<미정: …>` 목록, 없으면 "없음">
정리가 필요한 상태: <새 룰을 이미 어기고 있는 기존 문장·구조, 공통 룰과 충돌하는 하위 디렉토리 룰, 32KiB를 넘는 진입 파일, 없으면 "없음">
확인 방법: `git diff`(커밋했으면 `git show`)로 변경을 보고, `AGENTS.md`의 「공통 룰 적용 기록」 절에서 결정을 확인한다.
```

## 다시 실행할 때 (재적용·버전 올리기)

적용 기록이 있는 리포에서는 전체를 다시 대조하지 않는다. 먼저 ID 주석의 출처 표시를 확인하고(바로 아래), 그다음 아래 다섯만 대조한다.

| 대상 | 찾는 법 | 처리 |
|---|---|---|
| 새로 생긴 룰 | 제목의 `(vN 추가)`에서 N이 기록된 버전보다 크다 | 처음 적용할 때처럼 3단계와 4단계로 판정한다 |
| 바뀐 룰 | 제목의 `(vN 변경)`에서 N이 기록된 버전보다 크다 | 아래 「바뀐 룰」을 따른다 |
| 삭제된 룰 | 제목의 `(vN 삭제)`에서 N이 기록된 버전보다 크다 | 아래 「삭제된 룰」을 따른다 |
| 미결정 항목 | 적용 기록의 `미결정(…)` 줄 | 버전이 그대로여도 다시 판정하고 다시 묻는다. 결정되면 그 줄을 결정 내용으로 바꾼다 |
| 전제·도구 | 전제 태그 넷과 `rules.md`의 도구 의존 표 전체 | 아래 「전제와 도구」를 따른다 |

기록에 있는 결정(`기존 유지`·`조정`·`제외`)은 다시 묻지 않는다. 예외는 결정이 기록된 룰이 바뀌었고 그 변경이 결정과 무관하다고 볼 수 없는 경우 하나다(「바뀐 룰」). 대조할 것이 하나도 없으면 바꿀 것이 없다고 보고하고 끝낸다.

### 출처 표시부터 확인한다

`기존` 표시는 v15부터 쓴다. 그 전에 적용한 리포에는 사용자 문장에도 표시 없는 ID 주석이 달려 있다. 적용 기록에 `출처 표시: 확인함` 줄이 없으면, 다른 일을 하기 전에 리포의 **모든** ID 주석을 한 번 훑어 사용자 문장에 `기존`을 붙인다. 이번에 바뀐 룰의 문장만 보면 안 된다. 나머지 문장이 표시 없이 남아, 다음 버전에서 스킬이 쓴 문장으로 잘못 읽힌다.

- 주석마다 `git log -S '<ID 주석>' -- <파일>`로 그 주석이 들어온 커밋을 찾아 diff를 본다. 주석이 붙은 줄이 `+` 줄에만 있으면 스킬이 쓴 문장이다(스킬이 새로 만든 파일의 문장도 여기에 든다). 같은 문장이 `-` 줄에도 있으면(있던 문장에 주석만 붙었거나 뒤에 덧붙여 보강됐으면) 사용자 문장이다. 스킬은 작업 트리가 깨끗할 때만 실행되므로(1단계) 사용자 문장은 그 커밋보다 먼저 리포에 있었다.
- 이름이 바뀐 파일은 `--follow`를 붙여 원래 커밋까지 따라간다. 그 커밋이 적용 기록을 함께 고치지 않았거나(공통 룰을 적용한 커밋이 아니다) 리포의 첫 커밋이면, 판단할 수 없으므로 사용자 문장으로 본다. `기존`을 잘못 붙이면 다음에 한 번 더 묻게 될 뿐이지만, 잘못 빼면 사용자 문장을 묻지 않고 고치게 된다.
- 모두 확인했으면 적용 기록에 `- 출처 표시: 확인함(YYYY-MM-DD)`을 남긴다. 이 확인은 묻지 않고 한다.

### 바뀐 룰

먼저 새 룰을, 그 룰의 옛 문장을 뺀 **나머지 기존 룰 전체**와 4단계로 대조한다. 새 내용이 리포의 다른 문장이나 기록된 결정과 충돌하면 그 부분은 충돌로 묻고, 충돌하지 않는 부분만 아래대로 반영한다.

그다음 룰 ID 주석으로 그 룰의 문장을 찾는다.

- **이미 새 룰을 충족한다** — 그대로 둔다.
- **스킬이 쓴 문장이다**(`기존` 표시가 없는 ID 주석) — 묻지 않고 **그 자리에서** 새 룰에 맞게 고친다. 옛 문장 옆에 덧붙이지 않는다. 고친 곳은 보고서의 「갱신한 문장」에 적는다.
- **사용자 문장이다**(`기존` 표시) — 4단계로 다시 판정한다. 보강이면 덧붙이고 `기존` 표시는 그대로 둔다. 충돌이면 묻고, 답이 교체면 그 자리에서 고치고 `기존`을 떼며, 유지면 ID 주석을 떼고 적용 기록에 남긴다.
- **ID 주석이 없다** — 전제(3단계)로 빠져 있는 룰이면 그대로 둔다. 적용 기록에 `기존 유지`·`조정`·`제외`로 적힌 룰이면 아래 「결정이 기록된 룰」을 따른다. 그 밖에는 4단계로 판정한다.

두 가지를 더 본다.

- **`[outward]` 룰.** 리포 밖으로 나가는 행동이 새로 생기거나 넓어졌으면, 스킬이 쓴 문장이라도 고치기 전에 확인한다(4단계의 `[outward]` 규칙). 좁아지기만 했으면 묻지 않는다. 넓어졌는지 애매하면 넓어진 것으로 본다.
- **결정이 기록된 룰.** `rules.md` 끝 「변경 이력」의 해당 버전 항목과 적용 기록에 적힌 결정 사유를 읽는다. 바뀐 내용이 그 결정과 무관하다고 분명히 말할 수 있을 때만 결정을 그대로 두고 나머지를 반영한다. 그렇지 않으면 이전 결정과 날짜를 질문에 함께 보여 주고 다시 묻는다.

### 삭제된 룰

다른 대상보다 먼저 처리한다. 그래야 지운 룰의 미결정 줄을 「미결정 항목」이 다시 묻지 않는다. 예외는 `미결정(삭제)` 줄이다. 이전 실행이 지우지 못한 문장이 있다는 표시이므로, 버전이 그대로여도 「미결정 항목」이 집어 이 절차를 다시 밟는다.

먼저 룰 ID 주석으로 그 룰의 문장을 찾는다. 원칙은 스킬이 넣은 내용만 걷어 내고 사용자가 쓰거나 정한 내용은 묻지 않고 지우지 않는 것이다.

- **스킬이 쓴 문장이다**(`기존` 표시 없음) — 묻지 않고 문장을 지운다. 다만 적용 기록에 그 룰이 `조정`으로 적혀 있으면 사용자가 정한 문구이므로 지우기 전에 묻는다. 선택지는 둘이다.
  - **지운다**: 문장을 지운다. 그 룰의 `조정` 줄과 `미결정(삭제)` 줄도 함께 지운다.
  - **남긴다**: 문장은 이제 리포 고유 룰이 된다. ID 주석을 떼고 `조정` 줄과 `미결정(삭제)` 줄을 지운 뒤, 아래 「남은 사용자 문장」처럼 다시 대조한다.
  - 물을 수 없으면 문장과 `조정` 줄을 그대로 두고 `미결정(삭제)` 줄을 더한다.
- **사용자 문장이다**(`기존` 표시) — 사용자 글은 남기고 주석에서 지운 룰의 ID만 뺀다. 빼고 나서 남는 ID가 없으면 주석을 통째로 지운다(`<!-- 기존 -->`만 남기지 않는다). 그 줄에 스킬이 보강으로 덧붙인 부분이 있으면 그 부분만 지운다. 덧붙인 부분은 「출처 표시부터 확인한다」와 같은 방법(`git log -S`로 주석이 들어온 커밋의 diff를 보고 `+` 줄에만 있는 부분)으로 가린다. 가릴 수 없으면 묻는다.
- **ID 주석이 없다** — 문장에는 할 일이 없다.
- 한 주석에 여러 ID가 달려 있어 어느 부분이 지운 룰에서 왔는지 가릴 수 없으면 묻는다.

**남은 사용자 문장**은 다시 대조한다. 지운 룰이 다른 룰의 예외였다면 사용자 문장이 이제 다른 공통 룰과 충돌할 수 있다. 예를 들어 지운 룰이 "이때는 직접 고쳐도 된다"였다면, 같은 뜻의 사용자 문장은 "한 줄도 직접 고치지 않는다"와 부딪힌다. 그래서 ID를 뺀 사용자 문장을 리포에 들어간 나머지 공통 룰과 4단계로 대조한다. 충돌이면 묻고, 답에 따라 처리한다.

적용 기록은 줄마다 다음처럼 고친다.

- 줄의 주어가 지운 룰이면(`조정: <지운 ID> — …`, `미결정(충돌): <지운 ID> — …`) 그 줄을 지운다. 다만 문장을 지우지 못하고 남겼으면 그 룰의 `조정` 줄은 두고 `미결정(삭제)` 줄을 더한다. 문장이 남아 있는 한 그 문장이 사용자 결정이라는 기록도 남아야, 다음 실행이 스킬 문장으로 착각해 묻지 않고 지우지 않는다.
- 지운 룰이 목록의 하나로만 들어 있으면(`해당 룰: …`, 버전 줄의 `대상: …`) 그 ID만 뺀다.
- `종속: <지운 ID>`인 줄은 원인이 사라졌으므로 종속을 풀고, 그 룰을 4단계로 다시 판정한다.

지운 문장을 가리키던 다른 문장(링크, 지운 룰 ID를 인용한 참조)이 남으면 출처에 따라 처리한다. 스킬이 쓴 문장이면 참조를 걷어 내고, 사용자 문장이면 보고서의 「정리가 필요한 상태」에 적는다.

지우거나 ID를 뺀 곳은 보고서의 「지운 문장」에 적는다. 리포에 그 룰의 문장도 기록 줄도 없으면(전제로 빠져 있던 룰 등) 할 일이 없다. 이 경우 대조할 것이 없는 것으로 보되, 버전 줄은 새 버전으로 올린다.

### 전제와 도구

- 전제는 근거를 다시 본다. 사용자 결정으로 적힌 `해당 없음`은 다시 묻지 않는다. 전제가 새로 충족되면 그 태그가 붙은 룰 전부(`(vN 삭제)` 제외)를 4단계로 판정한다.
- 도구는 표 전체를 다시 확인한다. 이전 기록 뒤에 표에 새로 들어온 도구와 최소 버전도 대상이다. 이제 있는 도구의 `도구 없음` 줄은 지운다. 사용자 결정으로 적힌 `도구 없음`은 도구가 여전히 없어도 다시 묻지 않고 보고서의 도구 없음 경고에만 적는다. 묻지 못해 남긴 `도구 없음`과 이번에 처음 없는 것으로 드러난 도구는 3단계대로 묻는다.

### 적용 기록 갱신

버전 줄을 새 버전으로 바꾸고, 괄호 안에 어느 버전에서 올렸는지와 이번에 대조한 룰을 적는다: `- 버전: common-rules v15 (YYYY-MM-DD 적용. v13 → v15, 대상: R-GIT-02·R-ROLE-12)`. 결정된 미결정 줄은 결정 내용으로 바꾼다.

## 물을 수 없을 때 (비대화형 실행)

서브에이전트나 비대화형 실행처럼 AskUserQuestion을 쓸 수 없으면, 질문이 필요한 자리마다 **가장 덜 침습적인 쪽**을 고르고 그 사실을 적용 기록에 남긴다. 사용자가 나중에 다시 실행해서 결정할 수 있게 하는 것이 목적이므로, 보류한 결정(충돌·전제·`[outward]`·도구·읽힘·재확인)은 빠짐없이 적용 기록의 `미결정(…)`이나 `도구 없음` 줄로 남아야 한다. 다음 실행은 이 줄들로 다시 물을 것을 찾는다. 기록 위치와 문서 구조처럼 그 실행에서 굳는 배치 선택은 보고서에만 적는다.

| 원래 묻는 것 | 물을 수 없을 때 |
|---|---|
| 미커밋 변경이 있는데 계속할지 | 중단하고 보고한다 |
| Orca가 없는데 계속할지 | 계속한다. Orca 룰은 그대로 넣고 적용 기록과 보고서에 "도구 없음: Orca"로 남긴다 |
| 없는 도구(`gh`·worktree-teardown·`ccg`·`ego-browser`·humanize-korean)에 기대는 룰을 넣을지 | 넣는다. 설치는 하지 않는다. 적용 기록에 "도구 없음(비대화형 실행이라 묻지 못함)"으로, 보고서에 도구 없음 경고로 남긴다 |
| 근거 없는 전제 범주를 넣을지 | 넣지 않는다. 적용 기록에 "미결정(전제)"으로 남긴다 |
| 충돌 처리(관례 충돌 포함) | 반영하지 않고 기존 룰·관례를 그대로 둔다. "미결정(충돌)"·"미결정(관례 충돌)"로 남기고, 종속 룰도 함께 남긴다. 일부 충돌이면 지킬 수 있는 부분만 넣는다 |
| `[outward]` 룰을 넣을지(다시 실행할 때 넓어진 부분 포함) | 리포 밖으로 나가는 부분만 넣지 않고 "미결정(outward)"으로 남긴다. 나머지 부분은 넣는다 |
| 적용 기록 위치(R-DOC-01과 부딪힐 때) | `AGENTS.md` 끝에 쓰고 보고서에 적는다 |
| 전제 근거가 엇갈릴 때 | 넣지 않는다. "미결정(전제)"으로 남기고 엇갈린 근거를 적는다 |
| 새 문서 구조(새 폴더 체계)를 만들지 | 만들지 않는다. `AGENTS.md`(없으면 `CLAUDE.md`, 둘 다 없으면 새 `AGENTS.md`)에 절로 넣는다. 이미 있는 규칙 폴더 안에 새 파일을 만드는 것은 질문 대상이 아니므로 그대로 한다(`layout.md` §1) |
| `CLAUDE.md`에 `@AGENTS.md`를 넣을지 | 넣지 않는다. 적용 기록에 "미결정(읽힘)"으로 남기고 보고서의 「읽히지 않는 룰」에 적는다 |
| 결정이 기록된 룰이 바뀌어 다시 물어야 할 때 | 이전 결정을 유지하고 적용 기록에 "미결정(재확인)"으로 남긴다 |
| 삭제된 룰의 문장을 지울지(`조정` 문장, 출처를 가릴 수 없는 부분) | 지우지 않는다. 그 룰의 `조정` 줄은 두고 적용 기록에 "미결정(삭제)"를 더한다. 다음 실행은 이 줄을 「미결정 항목」으로 집어 「삭제된 룰」 절차를 다시 밟는다 |

## 공통 룰 자체를 고칠 때

룰을 추가·변경하려면 `references/rules.md`를 고치고 머리의 버전을 올린다. 바뀐 룰의 ID 옆에 `(v2 변경)`처럼 표시해 두면, 이미 적용한 리포에서 다시 실행할 때 그 룰만 대조한다. 파일 끝 「변경 이력」에 바뀐 룰 ID와 배경을 한두 줄 남긴다. 새 룰은 번호를 다시 매기지 말고 그 범주의 다음 번호를 쓴다. 이미 적용한 리포의 ID 주석이 어긋나지 않게 하기 위해서다. 위치는 주제가 가까운 룰 옆에 두어도 된다.

룰을 지울 때는 헤딩을 지우지 않는다. 제목 끝을 `(vN 삭제)`로 바꾸고, 본문은 `- 룰: 삭제됨.`으로 시작하는 줄과 `- 이유:` 줄만 남긴다. 같은 일을 맡는 룰이 있으면 룰 줄에 그 ID를 적는다. 헤딩이 남아야 이미 적용한 리포에서 다시 실행할 때 「삭제된 룰」로 찾아 걷어 낼 수 있다. 지운 번호는 다시 쓰지 않는다. 그 ID를 가리키는 곳도 모두 고친다. 범위는 도구 의존 표, 다른 룰 본문, `references/layout.md` §2 기본 구조, 이 문서, README다. `01～11`처럼 지운 번호를 사이에 둔 묶음 표기도 포함한다. 변경 이력은 그대로 둔다.

카탈로그 밖에서 함께 맞출 곳이 셋 있다. 플러그인 리포의 `tests/test_common_rules.py`가 앞의 둘을 확인한다.

- `.claude-plugin/plugin.json`의 버전(`0.N.0`)과 README 두 개의 버전 표기
- 새 룰이면 `references/layout.md` §2 기본 구조에서 그 룰이 들어갈 자리
- 새 도구가 필요하면 `rules.md`의 도구 의존 표, 이 문서 3단계와 「물을 수 없을 때」의 도구 목록, README의 도구 목록
